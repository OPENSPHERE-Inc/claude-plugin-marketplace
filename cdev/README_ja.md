# cdev

*[English README](README.md)*

Claude Code 向けのチームネイティブなマルチエージェントコーディングワークフロー。
`/cdev:coding` がエージェントチームを立ち上げ、タスクを設計から検証・レビュー済みの
コードまで駆動します。`/cdev:loop` は、`/cdev:coding` と creview の `/creview:rounds` を、
実装からレビューまでの無人の 1 本のパイプラインとして実行します。

## スキル

| コマンド | 目的 |
|---------|---------|
| `/cdev:coding` | コーディングタスクをエンドツーエンドで実装する。常駐チームを結成し、設計セル → コードセル → ドキュメントセル → QA ゲートをフィードバックループ付きで実行する。各セルでは producer とレビュアーがペアを組む。AI 向けプロンプトファイルにはセルフチェック・圧縮・解釈テストも行う。 |
| `/cdev:loop` | コーディングタスクを、判断を仰がずに `/cdev:coding` と `/creview:rounds` に通す。レビューが発散すると `/cdev:coding` へ差し戻し、ポストモーテムで終了かやり直しかを決める。どちらも上限の内で行う。[ループ](#ループcdevloop)参照。 |

どちらもタスク説明を添えて起動します。例: `/cdev:coding アップロードエンドポイントに
レートリミッタを追加`、`/cdev:loop --max-generations 2 アップロードエンドポイントに
レートリミッタを追加`。

## ライフサイクル上の役割

`cdev` はマーケットプレースのライフサイクルの**実装ステージ**です。動作する自己点検済みの
初版を素早く作ることに最適化します。インループのレビューは**品質ゲート**であって権威ある
レビューではありません。権威あるレビューは後段の `creview`（`/creview:start` → `triage` →
`respond` → `resolve`）で実施してください。権威レビューを `creview` に委ねるため、`cdev`
は速度と一貫性に振っています。

`/cdev:loop` は 2 つのステージを 1 本のパイプラインにまとめます。`/cdev:coding` の後に
`/creview:rounds` を実行し、発散時の `/cdev:coding` への差し戻しと、ポストモーテム後の
やり直しによって、レビューの結果を実装ステージへ戻します。

## 仕組み

`/cdev:coding` のリーダー（チームリード）は、選定した各専門家を名前付きの常駐
バックグラウンド teammate として（`Agent` の `run_in_background`）一度だけ spawn し、
各 producer にレビュアーをペアリングして、設計セル、チームの再編成、コードセル、
ドキュメントセル、最終 QA ゲート、コミットを駆動し、進捗をコンソールへ報告します:

1. **設計セル** — 各アーキテクトが担当領域の設計を書き、**ペアのレビュアー**がレビュー。
   アーキテクトが各指摘を **triage（修正 or 理由付きで却下）**、レビュアーが **resolve** して
   セルをクローズする。両者とも `rules/divergence.md` に従う: 後段のレビューを発散させる
   （修正が次の指摘を生み続ける）源泉 — 未確定の仕様・不変条件、方式が閉じきれない
   問題クラス、裁定されていない要求の相反、既存設計との不整合、ゴールと契約に必要な以上に
   手続きを細かく指定した AI 向けプロンプト — を設計に持ち込まず、レビュアーは見つけたものを
   Major 以上として指摘する。
2. **チームの再編成** — 全設計セルのクローズ後、`dev-helper` が設計とロスターを読み、設計が
   追加・変更する各ファイルが、そのファイルの領域に合うレビュアーと組むコーダーかライターの
   ちょうど 1 人のスコープに入るよう、コーダーとライターを再編成する。ドキュメントファイルは
   ライターにだけ渡し、ライターのスコープはほかのファイルを含まない（[ドキュメント](#ドキュメント)
   参照）。チーム結成と同じく、プロンプトファイルはほかのソースを含まないスコープのコーダーに
   だけ渡す。設計が追加するテストは、テスト対象のファイルがプロンプトファイルでもドキュメント
   ファイルでもなく、それを持つコーダーがいれば、そのコーダーに渡す。ファイルがそれを持てない
   コーダーかライターのスコープの下にあればそのスコープから外し、持てる既存のコーダーか
   ライターがいなければ新しいコーダーかライターに渡す。リーダーは、更新されたロスターが加える
   コーダー・ライター・レビュアーを起動する。1 回の差し戻しの後も更新されたロスターが使えなければ、
   元のロスターのままコーディングを始め、最終報告でそのことを示す。
3. **コードセル** — 各コーダーが自スコープを実装（テストスイートがあればテストファースト）。
   コメントがあれば `comment-sensei` がコメント違反を修正し、AI 向けプロンプトファイルは
   `prompt-sensei` がセルフチェックと圧縮を行う（[AI 向けプロンプト](#ai-向けプロンプト)
   参照）。**ペアのレビュアー**がレビューし、コーダーが triage、レビュアーが resolve して
   セルをクローズする。設計がドキュメントファイル以外のファイルを挙げなければ、コードセルは
   回らない。
4. **ドキュメントセル** — 設計がドキュメントファイルを挙げるとき、全コードセルのクローズ後に、
   各ライターが自スコープのドキュメントファイルを、設計と、この実行の変更を含むその時点の
   コードをもとに書く。**ペアのレビュアー**がコードとの整合を含めてレビューし、ライターが
   triage、レビュアーが resolve してセルをクローズする。
5. **QA ゲート** — ビルド / フォーマット / テストを 1 回実行し、タスクに AI 向けプロンプト
   ファイルがあれば、変更されたプロンプトの解釈テストも併せて行う。失敗時は担当コーダーが
   修正し、その修正もレビューセルを通してから QA を再実行する（上限付きループ）。ライターの
   スコープにあるドキュメントファイルの失敗は代わりにそのライターが直す。また、コーダーの
   修正でコードが変わった後は、各ライターがドキュメントをコードに合わせ直す。どちらも QA の
   再実行の前にドキュメントセルとして回る。
6. **コミット** — `--commit` のとき、`dev-helper` が実行の変更を論理的な変更ごとのコミットに
   分ける計画を書き、`scripts/commit-plan.py` が計画を検査してコミットを作る。受理できる計画が
   得られなければ、変更を 1 回でコミットする。

セルは自律的に回ります: producer（アーキテクト / コーダー / ライター）とペアのレビュアーが
review ⇄ triage ⇄ resolve をレビュアーがクローズするまで反復します。リーダーはセルを設定し、
ステップゲート（全設計セルのクローズとチームの再編成の後にコーディング、全コードセルがクローズ
してからドキュメントセル、全コードセルと全ドキュメントセルがクローズしてから QA）を守らせ、
QA ゲートを実行し、エスカレーションを裁定します。レビュアーと producer が `Critical` 指摘で
デッドロックした場合、レビュアーはリーダーへエスカレーションし、リーダーでも裁決できなければ
ユーザーに諮り `FIXME:` を残します。判断の優先順位は ①ユーザーの初期指示 → ②設計意図。
ドキュメントセルでは、コードが何をするかについての記述は、これらに優先してコードに合わせます
（[ドキュメント](#ドキュメント)参照）。権威あるレビューは `creview` なので、未解決はブロック
せず `FIXME:` として残します。

teammate はステップをまたいで常駐するため、各自が文脈を保持し増分的に改訂します。
フィードバックは**ピア間**で流れ、リーダーはロスター・ペアリング・各セルの状態・重要度
カウント・パス・QA と解釈テストの結果・ライターが報告する設計やタスクからのコードの乖離のみを
保持し、本文は持ちません。

## 動作要件

`/cdev:coding` はバックグラウンドのサブエージェント（`Agent` の `run_in_background`）と、命名
teammate 間の `SendMessage` を使用します。セッションは単一の暗黙チームを持ち、チームの
明示的な作成・削除も共有タスクリストもありません（リーダーが各セルの状態を自前で追跡）。
実行の終了時、リーダーは `TaskStop` で teammate を停止します。
これらが利用可能なランタイムでのみ動作します。これは使い捨て・ステートレスなエージェント方式の
広い移植性よりも効率を優先した、意図的なトレードオフです。AI 向けプロンプトファイルの
解釈テストでは、teammate の `prompt-sensei` が `Agent` ツールでサブエージェントを起動します。
teammate がサブエージェントを起動できない場合、テストはそのファイルを未テストとして報告します。

Claude Code v2.1.217 以降は、セッション内で同時に実行中のサブエージェントの数を
`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`（デフォルト 20）で制限し、上限を超える起動を
`Concurrent subagent limit reached` で拒否します。作業中の teammate と解釈テストの
サブエージェントは、この数に入り得ます。リーダーは、拒否された teammate を、teammate の
報告か完了通知で次に起こされたときに spawn し直します。リーダーを起こす teammate が
残っていなければ、実行はそのエラーで終了します。その場合は、セッション内のほかの
エージェントの終了を待つか上限を引き上げてから、再実行してください。実行はコミットしません。
ただし、`--commit-always` が有効で、拒否がすべてのコードセルとドキュメントセルが閉じた後の
QA ゲートで起きた場合は、そのオプションのとおりコミットし、以降の未コミットの変更と残る
ワークツリーについての説明は当てはまりません。`--worktree` なしの場合、エラーまでの変更は
作業ツリーに未コミットのまま残り、実行が新しく作ったファイルは未追跡のまま残ります。
次の実行の開始時に行う
クリーンな作業ツリーの確認は、未追跡のファイルも数え、
`.claude/tmp/`・`.claude/worktrees/`・`--output` の指定先・`--handoff` と `--result` の
ファイルは除外します。その外にある変更を、先にコミットするか、退避するか、破棄してください。
`--worktree` 時は変更がワークツリーに残り、そのワークツリーは削除せずにパスを報告します。

`prompt-sensei` は、拒否されたテスト用サブエージェントを、自分が起動したものが返った後に
起動し直します。まとめて試みたテスト用サブエージェントの起動が 1 件も通らず、自分が起動した
もので実行中のものもないときは、起動を拒否されたサブエージェントのファイルは未テストとして
報告されます。

このスキルは、`--worktree` の有無にかかわらずリポジトリルートで起動したセッションを必要とし、
リポジトリのサブディレクトリから起動した場合はエラーで終了します。

同梱の `fetch-diff.sh` / `del-tmp.sh` スクリプトは、`PATH` 上の `python3`（3.9 以降）も
必要とします。両者が共有する `.claude/tmp/` 封じ込めチェックは
`scripts/lib/scratch-guard.py` に実装されています。コミットのステップと
`/cdev:loop --cleanup` が実行する `scripts/commit-plan.py` も、`python3` を必要とします。
コミットのステップがコミットを分けるのは Git 2.25 以降の場合だけで、それより古い Git では
1 回でコミットし、その理由を報告します。

プロジェクトの `.claude`、`.claude/tmp`、`.claude/worktrees` はシンボリックリンクにできません。
リンク先がプロジェクト内でも、同梱スクリプトがエラーで拒否します。作業ツリー間で
設定を共有する場合は、`~/.claude/` に置いてください。

`/cdev:loop` は `/cdev:coding` と `/creview:rounds` の両方の要件を持ちます。
[要件とコスト](#要件とコスト)を参照してください。

## オプション

`/cdev:coding` のオプションです。`/cdev:loop` のオプションは[ループ](#ループcdevloop)を
参照してください。

- `--review-rounds N`（既定 5、最大 10）— セルごとの review ⇄ triage の最大反復回数。
- `--qa-attempts N`（既定 5、最大 10）— QA 検証 ⇄ コーダー修正の最大試行回数。
- `--commit`（既定 off）— 検証済みの実装を、論理的な変更ごとのコミットに分けてコミットする。
  メッセージはリポジトリのコミット履歴と規約に従う。
  - 変更された各ファイルは、ちょうど 1 つのコミットに入る。1 つのファイルの変更を複数の
    コミットに分けることはない。
  - 受理できる計画が得られないとき、またはコミットが途中で失敗したときは、残りを 1 回で
    コミットし、その理由を報告する。
  - 最後より前のコミットはビルドもテストもしない。QA が検証したのは最終状態だけである。
- `--worktree[=branch]`（既定 off）— タスクを `branch` 上の別の git ワークツリーで実行する。
  `--commit` も有効になる（後述）。
- `--output {dir}` — 設計ドキュメントの出力先ディレクトリ（既定
  `.claude/tmp/cdev-coding-{timestamp}-design/`）。
- `--handoff {path}`（既定なし）— チーム結成・設計セル・設計レビューが読む、Markdown の
  申し送り。
  - 判断の優先順位は、ユーザーのタスク、申し送り、設計意図の順になる。
  - 申し送りが戻り先としてターニングポイント（コミットとともに示すブランチ）を挙げるとき、
    アーキテクトは担当領域のファイルをターニングポイントの内容に戻すことを選べる。
    - メイン作業ツリーの無視ファイル（`.env` など）を上書きしないよう、戻すのは `--worktree`
      を指定した実行だけである。指定しない実行では、申し送りがターニングポイントを挙げても、
      設計は現在のコードの上に組み立てる。
    - 戻すのはファイルの内容だけで、ブランチと HEAD は動かさず、戻した内容はこの実行の
      変更として扱う。
    - 次のいずれかに当たる復元は拒否され、復元しようとしたパスは手を付けずに残る: 未追跡の
      ファイルかローカル変更のある追跡ファイルを上書き・削除する、復元するパスの外にあるパスを
      変える。実行はそのまま続き、拒否したパスとその理由を最終報告と結果ファイルが挙げる。
    - 復元リストはドキュメントファイルを挙げない。ドキュメントファイルをターニングポイントの
      内容に戻す設計は、代わりにそれをドキュメントの変更として挙げる。そのライターが同じ復元で
      その内容を取り（拒否される条件も同じ）、そのうえでコードについての記述をコードに合わせる
      （[ドキュメント](#ドキュメント)参照）。
  - 開始時からブランチか HEAD が動いていると、実行はコミットしない。
- `--team-tag {tag}`（既定なし）— すべての teammate 名に `-{tag}` を付ける
  （例: `coder-backend-g1c2`）。同じセッションで 2 回目以降に実行しても、前回の teammate と
  名前が重ならない。タグは英数字とハイフンの 1〜16 文字で、英数字で始まる。セッション内で
  未使用のタグを使うことは呼び出し側の責任とする。
- `--commit-always`（既定 off。`--commit` を含意）— すべてのコードセルとドキュメントセルが
  クローズした後に、QA や解釈テストが未通過でもコミットする。未通過だったことは結果ファイルと
  最終報告が示す。
- `--result {path}`（既定なし）— 終わりに結果を JSON で書く。コミットの有無、最後のコミット、
  コミットの数、1 回のコミットへのフォールバックなどのコミットのステップの警告、ブランチ、
  設計ドキュメントのパス、設計が復元元とするターニングポイント、拒否された復元とその理由、
  QA と解釈テストの結果、残した `FIXME:` とエスカレーションの数、チームの再編成が
  元のロスターにフォールバックしたか、ライターが報告する設計やタスクからのコードの乖離、
  途中で止まったときのステップと理由、残ったワークツリーを持つ。不正なオプションや要件の
  未達など、コミットのステップに至らずに終わるときも書く。`.claude` か `.claude/tmp` が
  シンボリックリンクのときは書かない。
  - そのときのほか、中断されたときや書き出しに失敗したときなど、ファイルを書かなかった場合は、
    そのパスにある既存のファイルが残り、今回の結果と取り違えられうる。既存のファイルがない
    パスを渡すか、実行前にそのファイルを削除したうえで、ファイルがないことをエラーとして扱う。

設計ドキュメント（`design-{slug}.md`。アーキテクトごとに 1 つ）は実行後も残し、それ以外の
中間ファイルは削除します。`--commit` は設計ドキュメントも、`--handoff` と `--result` の
ファイルもステージしません。開始時のクリーンな作業ツリーの確認は `.claude/tmp/`・
`.claude/worktrees/`・`--output` の指定先・`--handoff` と `--result` のファイルを
除外するため、過去の実行が残した設計ドキュメントや `--worktree` 実行のワークツリーは
次の実行を妨げません。

`--worktree` を指定すると、チームは `.claude/worktrees/` 配下の別の git ワークツリーで作業
します。メイン作業ツリーのソースには触れず、メイン作業ツリーがクリーンである必要もありません。
ワークツリーは `branch` をチェックアウトします — 既存のローカルブランチはそのまま、存在しない
場合は現在の HEAD から新規作成します。`=branch` を省略すると新しいブランチ
`cdev-coding-{timestamp}` を作成します。git は 1 つのブランチを 2 つのワークツリーで
チェックアウトできないため、メイン作業ツリーでチェックアウト中のブランチは指定できません。
ワークツリーはコミット済みの状態（新規ブランチなら現在の HEAD、既存のブランチならその先端）
から始まるため、メイン作業ツリーの未コミットの変更はタスクに含まれません。各 teammate は
ワークツリーを作業対象（`target_dir`）として受け取り、その配下・
実行の作業用ディレクトリ・タスクが指定する出力先にだけ書き込みます。タスク中のパスはそのまま
渡し、リポジトリ相対パスはワークツリー基準で解決し、メイン作業ツリーを指す絶対パスは参照専用と
します。gitignore 対象の依存物・仮想環境・ビルドディレクトリ・`.env` や、
`git worktree add` が初期化しないサブモジュールの中身もワークツリーには存在しないため、
ビルドとテストは新規チェックアウトで通る必要があります。依存のインストール等は
`build-format.md` の configure コマンドに含められますが、configure はビルド段の冒頭でのみ
実行されます（format コマンドより後で、ビルドがスキップされた場合や Build が宣言されていない
場合は実行されません）。そのため、format コマンドとビルドなしで走るテストは configure に
依存できません。そうした前提物の欠落によるビルド／テストの失敗はソースで修正せず、QA ゲートは
QA 修正セルを回さずに終了し、環境起因の失敗として報告します。
作業用ディレクトリと既定の設計ドキュメントの出力先はメイン作業ツリーの
`.claude/tmp/` に置かれ、相対パスの `--output`・`--handoff`・`--result` はメイン作業ツリーの
ルートを基点に解決します。
移植先プロジェクトの `.claude/agents/` と `.claude/rules/` もメイン作業ツリーのものを読みます。
終了時にワークツリーは削除され、ブランチは残ります。未コミットの変更が残ったワークツリー
（例: QA 失敗が未修正のまま終わった場合）は削除せず、そのパスを報告します。サブモジュールを
初期化したワークツリー（configure で初期化した場合など）も git が削除を拒否するため、同様に
残してパスを報告します。内容を確認のうえ `git worktree remove --force <パス>` で削除して
ください。残っている間は、同じブランチを指定した `--worktree=branch` の再実行が失敗します。

## AI 向けプロンプト

AI エージェントが自身への指示として読むファイル — エージェント定義、スキル（`SKILL.md`）、
スラッシュコマンド、ルール、スキルがエージェントに読ませるプロンプトテンプレート — は
AI 向けプロンプトです（`rules/prompt.md`）。`CLAUDE.md` などのプロジェクトのメモリファイルと
markdown の出力テンプレートは含みません。プロジェクトのメモリファイルは代わりにドキュメントと
して扱います（[ドキュメント](#ドキュメント)参照）。このスキルが変更できるのはリポジトリ内の
プロンプトファイルだけで、`~/.claude/` 配下などリポジトリ外のものは扱えません。teammate は
作業対象の中にだけ書き込むためです。ほかの実行と同じく、プロンプトファイルを編集する実行も
`--worktree` を使わない限りクリーンな作業ツリーが必要です。プロンプトファイルを作成・編集する
タスクも、ほかのタスクと同じ設計セル・コードセル・QA ゲートを通り、次の処理が加わります:

- チーム結成では、プロンプトファイルをほかのソースを含まないスコープのコーダーに割り当て、
  それぞれをプロンプト担当のレビュアーとペアにします。このレビュアーもほかのレビュアーと
  同じく、同梱の `prompt-sensei` を含むエージェントのプールから最も適合するものが選ばれます。
- コーダーはプロンプトを書くとき `rules/prompt.md` に従います。コードセルではレビューの前に、
  `prompt-sensei` teammate が、コーダーがプロンプトファイルで作成・変更した箇所を同ルールに
  照らしてセルフチェックし、違反を最大 2 回まで修正し、エージェントに求める内容を変えずに
  その箇所を圧縮します。既存ファイルのそれ以外の部分は、設計がファイル全体を対象としない限り
  そのまま残します。残った違反は、コーダーが変更とともにレビュアーへ渡します。
- 設計セルとコードセルは、プロンプトファイルの過剰指定を防ぎます（`rules/divergence.md`）:
  - ゴールと契約に必要な以上に細かい手続きはレビューのたびに新たな指摘を呼び、細部を足す
    修正が次のレビューの対象を増やします。
  - プロンプトが過剰指定かどうかと、そのゴールと契約が何かは、`rules/prompt.md` に照らして
    判定します。
  - 書き込み範囲や、信頼できない入力をデータとして扱う指示など、AI が判断に要する制約と前提は
    手続きではなく、プロンプトに残ります。
  - 細部の指摘とは、ゴールと契約を知っている AI なら既に正しく行える方法を足す、または
    精密化するだけの修正を求める指摘です。
  - レビュアーは、設計または実行がプロンプトファイルで作成・変更する箇所の過剰指定を指摘し、
    設計がファイル全体を対象とする場合はファイル全体を対象にします。ゴールと契約を明示して
    方法を AI に委ねる書き直しを推奨し、細部の指摘は挙げず、エッジケースの欠落も同じ基準で
    判定します。
  - コーダーは細部の指摘をこのルールを理由に却下し、方法が依拠するゴールか契約をプロンプトが
    まだ明示していなければ、却下せずにそれを明示します。
  - コーダーは、QA ゲートの解釈テストで不明瞭とされた項目も含め、プロンプトの手続きの欠落や
    曖昧さを手順を足して埋めず、関わるゴールか契約を明示して解消します。
  - アーキテクトは、設計がプロンプトファイルで作成・編集する箇所について、タスクがファイル
    全体を対象とする場合はファイル全体について、ゴールと契約を設計に記します。方法の欠落や
    曖昧さを同じ方針で解消し、どちらにも関わらないものは手順を足さずに AI に委ねます。
  - ユーザーのタスクが明示的に求める手続きと、コードセルではさらに設計が指定する手続きは
    過剰指定に含めず、プロンプトはそれを満たします。欠けていれば補います。
- QA ゲートでは、`prompt-sensei` が実行中に変更されたプロンプトファイルごとに解釈テストも
  実行します:
  - その実行で作成・変更した箇所について、入力が省略した値をエージェントがどう決めるか等の
    質問からなるチェックリストを作ります。
  - 新規起動のサブエージェントが、そのプロンプトと、プロンプトが読み手に読ませるファイル
    だけからチェックリストに回答します。このサブエージェントは実行の文脈を持たず、ファイルを
    読むことしかできません。
  - サブエージェントが回答できない項目があるファイルはテスト不合格となり、QA 修正セル
    （コーダーの修正をペアのレビュアーがレビューする）を通ってから QA を再実行します。
  - 再試行では、不合格または未テストだったファイル、QA 修正セルが対象としたファイル、
    前回の結果になかったプロンプトファイルを、各ファイルのチェックリストを引き継ぎ、
    前回の試行以降に変更された箇所の項目だけを加えて再テストします。
  - サブエージェントを起動できなかった等でテストできなかったファイルは未テストとして報告され、
    QA 修正セルを通らず、その実行はテストに合格しません。
  - テストはビルドやテストと同じ QA 試行の中で行われ、`--qa-attempts` が上限です。

## ドキュメント

ドキュメントは、`rules/document.md` が扱う人間向けのドキュメントです:

- README、API リファレンス、ガイド、変更履歴などのファイル。
- `CLAUDE.md` や `AGENTS.md` などのプロジェクトのメモリファイル。`rules/prompt.md` が AI 向け
  プロンプトから除外しているものです。

次のものはドキュメントではありません:

- AI 向けプロンプトファイル。コードセルを通ります（[AI 向けプロンプト](#ai-向けプロンプト)
  参照）。
- ソースコードとその中のコメント（docstring を含む）。
- テスト。
- プロンプトファイルから外部化した markdown の出力テンプレート。そのプロンプトファイルの
  コーダーが持ちます。
- 実行の設計セルが書く設計ドキュメント。

この定義は `rules/teammate.md` § Documentation files にあります。アーキテクトは、設計が挙げる
各ファイルをファイル単位で分類し、設計レビューがその分類を確かめます。ドキュメントファイルを
変更するタスクは、次のように進みます:

- **ライター** — チーム結成とチームの再編成は、ドキュメントを独立したドメインとして扱います。
  - ドキュメントファイルはライター（`writer-{slug}`）にだけ渡し、ライターのスコープはほかの
    ファイルを含みません。
  - 各ライターは、ドメインがそのドキュメントをカバーするレビュアーとペアを組みます。
  - アーキテクトのスコープは、コードとそれを説明するドキュメントを一緒に含められ、1 つの設計が
    両方を扱います。
- **ドキュメントセルが回るとき** — QA ゲートの前には、クローズした設計が変更するファイルに
  ドキュメントファイルを挙げる場合に限り、全コードセルのクローズ後に回ります。
  - 設計がほかのファイルを挙げなければ、コードセルは回らず、ドキュメントセルだけが回ります。
  - チームの再編成が元のロスターにフォールバックし、そのロスターにライターがいなければ、
    設計が挙げるドキュメントは書かれません。コンソールと最終報告がそのことを示します。
- **コードに合わせて書く** — ライターは、設計と、この実行の変更を含む作業対象のその時点の
  コードをもとに書きます。
  - コードが何をするかについての記述はコードに合わせ、コードはタスク・申し送り・設計に優先します。
    これらが決めるのは何をドキュメント化するかだけです。
  - コードが設計やタスクと食い違うとき、ライターはコードのとおりに書き、その乖離を報告します。
    実行はコードを直しません。
  - 乖離は最終報告と結果ファイルの `doc_departures` に、`/cdev:loop` の下では `state.jsonl` と
    `loop-summary.md` の警告にも現れます。
- **レビュー** — ペアのレビュアーは、ライターのスコープのドキュメントを、この実行の変更を
  含むコードに照らして確かめます:
  - 変更したファイルが記述する挙動・インターフェース・オプション・既定値・パス・要件・例が
    コードと整合するか。
  - この実行のコードの変更が、ライターのスコープのうちライターが変更しなかった部分を誤りに
    していないか。
  - 設計がライターのスコープに求めるドキュメントの変更がそろっているか。
  - 変更したファイル同士が矛盾しないか、プロジェクトのドキュメント規約と `rules/document.md`
    に従っているか。
  - ライターが報告する各乖離が成り立つか（成り立たなければ `Major`）。
- **重大度** — レビュアーは `Critical` と `Major` の指摘をライターに送ります。
  - `Critical`: 読み手が頼る点で、コードと矛盾する記述。
  - `Major`: 設計が求めるドキュメントの変更の欠落、ライターが報告していない設計やタスクからの
    コードの乖離、読み手をコードの誤った使い方に導く記述、レンダリングを壊す記法。
  - `Minor` 以下: 読み手を誤らせない文言や体裁。
  - ドキュメントをコードに反して設計やタスクに合わせることを求める指摘はしません。報告されて
    いない乖離は、それを報告することで解消します。
  - この実行が変更しておらず、誤りにもしていない記述は対象外で、挙げても `Info` です。
- **QA ゲート** — QA はドキュメントセルの後に走るため、フォーマット・ビルド・テストの
  ワークフローはドキュメントも対象にします。
  - QA 修正セルが回った試行では、それらのクローズ後、QA の再実行の前に、各ライターが
    ドキュメントセルをもう一度回し、ドキュメントをコードに合わせ直します。
  - QA が失敗したファイルとしてライターのスコープにあるファイルを報告したときは、設計が
    ドキュメントファイルを挙げていなくても、そのライターがドキュメントセルで直します。
  - どのライターのスコープにもない失敗したファイルは、ドキュメントであっても QA 修正セルが
    直します。
  - 最後の QA の後にファイルを変えるセルはありません。
- **その他の規則**
  - テスト駆動はドキュメントに適用しません。
  - ドキュメントセルで残す `FIXME:` は、ファイルの形式に合ったコメントにします。Markdown では
    `<!-- FIXME: ... -->` です。
  - 設計の復元リストはドキュメントファイルを挙げません。ドキュメントファイルをターニング
    ポイントの内容に戻すときは、設計が代わりにそれをドキュメントの変更として挙げます。
    - ライターは、ほかの変更より前に、復元リストと同じ復元でその内容を取ります。ファイルは
      ターニングポイントのコミットでの内容になり、そのコミットにファイルがなければ削除されます。
    - その復元は復元リストのものと同じ条件で拒否され、拒否されたものは理由とともに最終報告と
      結果ファイルに載ります。
    - ライターはそのうえで、コードについての記述をコードに合わせます。
    - これができるのは、ファイルを復元できる設計に限ります。すなわち、申し送りがその
      ターニングポイントを挙げる、`--worktree` を指定した実行です。

## ループ（/cdev:loop）

`/cdev:loop` は `/cdev:coding` と同じコーディングタスクを受け取り、判断を仰がずに実装から
レビューまでを通します。`/cdev:coding` と `/creview:rounds` をセッション内でインライン実行し、
それぞれのリーダーを務めますが、設計・コーディング・レビューを自ら行うことはありません。
レビューが発散すると上限まで `/cdev:coding` へ差し戻し、それ以外ではポストモーテムが、
終了するか開始コミットからやり直すかを決めます。どちらにも上限があるため、実行は必ず終わります。
push と PR の作成は行いません。

### 流れ

- **サイクル**は、`/cdev:coding` 1 回と、それに続く `/creview:rounds` 1 回の組です。
  **世代**は、1 本の作業ブランチ上の一連のサイクルで、**開始コミット**から始まります。
  開始コミットは、ループの開始時のメイン作業ツリーの `HEAD` です。
- 各サイクルでは、`/cdev:coding` が世代の作業ブランチのワークツリーで実行され、QA や
  解釈テストが未通過でも結果を論理的な変更ごとに分けてコミットします。続いて
  `/creview:rounds` が同じブランチで `--incremental` により実行され、発散を検出すると
  一時停止せずに止まります（`--on-divergence stop`）。
- どのサイクルのレビューも、Round 1 は世代全体を開始コミットからの差分としてレビューし、
  以降のラウンドは直前のラウンドの修正だけをレビューします。差し戻しはそれまでのラウンドの
  修正に横断的に手を入れうるため、その後のレビューは世代全体を見直します。
- **差し戻し**: レビューが発散で止まると、ループは、発散調査レポートの源泉と修正案に従うよう
  `/cdev:coding` に求める申し送りを書き、同じブランチで次のサイクルを始めます。
  - 第 2 世代以降では、申し送りは、その世代を始めたポストモーテムの申し送りの方針と、
    それが避けるとしたことも引き継ぎます。これらは発散調査レポートの修正案より優先します:
    これらから外れずには除けない源泉は残り、最大 `--max-sendbacks` 回の差し戻しを経て、
    その世代のポストモーテムに委ねられます。
  - 既定では、新しい作業をブランチの先頭に積み、それまでのレビューの修正を保ちます。その多くは
    発散と無関係だからです。
  - 設計は代わりに、同じ世代のターニングポイントの内容にファイルを戻すことを選べ、設計レビューが
    その妥当性を確かめます。戻した内容はブランチの先に積んでコミットし、履歴は書き換えません。
  - `--max-sendbacks` が世代あたりの差し戻し回数を制限します。上限を超えた発散は、未解消として
    ポストモーテムに渡ります。
- **ポストモーテム**: 世代のレビューが収束した、最大ラウンド数に達した、または差し戻しの上限を
  超えて発散したとき、ポストモーテムのサブエージェントが、その世代の設計ドキュメント、
  レビュードキュメント、最終レポート、発散調査レポートを読み、`finish` か `redo` を返します。
  - 既定では、次をすべて満たすときに限り `redo` を返します。
    - 成果物の品質に影響する問題が残る: 未解決の Critical / Major の指摘、それに付いた
      `FIXME:`、未通過の QA、未解消の発散。
    - その根本原因が設計の選択にあることを、レビュードキュメントが示す。
    - その原因を避ける別のアプローチを具体的に示せる。
  - `--pursuit` では、そうした問題が残らなくても、次をすべて満たすときは `redo` を返します。
    - 別のアプローチを具体的に示せる。
    - そのアプローチが、観察できる性質で世代を明確に上回ると見込める。たとえば、繰り返し
      指摘された問題の類型を生じなくする、設計が受け入れた制約や残存リスクを解消する、
      構成要素・インターフェース・特例の数が明確に減る、タスクが掲げる目標をよりよく満たす。
    - 設計ドキュメント、レビュードキュメント、コードがその見込みを裏付ける。
  - 通常の修正で届く改善や、好みの問題は `redo` の理由にしません。
  - `redo` は**グランドリセット**を始めます。ポストモーテムが書く申し送りとともに、新しい作業
    ブランチで開始コミットから新しい世代を始めます。上限は `--max-generations` です。残りの
    世代がなければ、判定は `finish` になります。
- **採用世代**: `finish` では、ポストモーテムが成果物とする世代を選びます。既定は最後の世代で、
  以前の世代がそれを上回るときに限り、その世代を採ります。上回るとは、未解決の Critical /
  Major の指摘、`FIXME:`、QA、未解消の発散の各点で劣らず、少なくとも 1 点で勝ることです。
  上回る以前の世代が複数あれば、そのうち他のどれにも上回られないものの中で最新の世代を採ります。
  ループは、その世代の作業ブランチの先頭に成果物ブランチを作ります。
  - `--cleanup` では、ループは代わりに、その世代の変更を開始コミットから論理的な変更ごとの
    コミットに積み直し、その最後のコミットに成果物ブランチを作ります。作業ブランチには元の
    履歴が残ります。

### オプション

- `--branch {name}`（既定 `cdev-loop-{timestamp}`）— 成果物ブランチの名前。作業ブランチと
  ターニングポイントの名前の接頭辞も兼ねる。
- `--max-sendbacks N`（既定 2、0〜5）— 世代あたりの差し戻しの最大回数。
- `--max-generations N`（既定 3、1〜5）— 最大世代数。1 ではグランドリセットを行わない。
- `--pursuit`（既定 off）— 上記のとおりポストモーテムの `redo` の条件を広げる。
- `--cleanup`（既定 off）— 通常終了で、上記のとおり採用世代の変更を積み直したコミット列の
  先頭に成果物ブランチを作る。
  - 計画者のサブエージェントが `/cdev:coding` のコミットのステップと同じ基準で変更を
    コミットに分け、`scripts/commit-plan.py` が計画を検査して、ref・インデックス・作業ツリーの
    どれにも触れずにコミットを作る。
  - 積み直しの最後のコミットは作業ブランチの先頭と同じツリーを持つため、QA とレビューの結果は
    そのまま当てはまる。それより前のコミットはビルドもテストもしない。
  - コミットは `git commit-tree` で作るため、フックは走らない。`commit.gpgSign` が真なら
    署名する。署名に対話が要る環境では積み直しが失敗し、[停止する場合](#停止する場合)の
    とおりフォールバックする。
  - 作者とコミッターは、現在の git の ID と現在時刻になる。
  - 開始コミットと世代の先頭のツリーが同じなら、積み直さない。
- `--output {dir}`（既定 `.claude/tmp/cdev-loop-{timestamp}/`）— 実行ディレクトリ。
- `/cdev:coding` へ渡すもの: `--review-rounds N`、`--qa-attempts N`。`/creview:rounds` へ
  渡すもの: `--max-rounds N`、`--adversarial`、`--adr`。
- エラーとして受け付けないもの: 常に有効な `--worktree`・`--commit`・`--incremental`、
  ユーザーの指示を待つ `--confirm`・`--confirm-round`、ループが決める `--base`、ループ自身が
  内側のスキルに渡すオプション（`--on-divergence`・`--result`・`--handoff`・`--team-tag`・
  `--commit-always`）。

### ブランチとターニングポイント

以下の名前の `{branch}` は `--branch` の値、`g` は世代、`c` はサイクルを表します。

| 種別 | 名前 | 作成時点 |
|------|------|---------|
| 成果物ブランチ | `{branch}` | 終了時。採用世代の作業ブランチの先頭に作る。`--cleanup` では、積み直したコミットの先頭に作る |
| 作業ブランチ | `{branch}-g{g}` | 世代 g の開始時。開始コミットに作る |
| ターニングポイント A | `{branch}-tp/g{g}c{c}-coding-start` | サイクル c の `/cdev:coding` の直前 |
| ターニングポイント B | `{branch}-tp/g{g}c{c}-coding-done` | サイクル c の `/cdev:coding` の直後 |

- ターニングポイントは、その時点のコードを示すブランチです。世代の最初のサイクルの
  ターニングポイント A は開始コミットで、以降のサイクルでは直前のレビューの後の作業ブランチの
  先頭です。ターニングポイント B は `/cdev:coding` のコミット後の先頭で、コミットしなかった
  ときは A と同じコミットになります。最後のレビューの後の状態は、作業ブランチの先頭が保持します。
- ループは、どの作業ツリーにも触れずにブランチを作り、ターニングポイントを動かしも消しもせず、
  作業ブランチの履歴を書き換えません。グランドリセットの後も、以前の世代の作業ブランチと
  ターニングポイントは残ります。後始末は利用者が行います。実行のターニングポイントを
  まとめて削除するには:

  ```
  git for-each-ref --format='%(refname:short)' 'refs/heads/{branch}-tp/' | xargs git branch -D
  ```

- ターニングポイントから手動で続けるには、そこからブランチを作ります。例:
  `git switch -c retry {branch}-tp/g1c1-coding-done`
- `{branch}` か `{branch}-tp` という名前のブランチ、`{branch}/` か `{branch}-tp/` 配下の
  ブランチ、`{branch}-g*` に当たるブランチが既にあると、実行は開始時に止まります。
  ターニングポイントを `{branch}/` ではなく `{branch}-tp/` 配下に置くのは、git がブランチ
  `{branch}` と `{branch}/` 配下のブランチを共存させられないためです。

### 実行ディレクトリ

```
{output}/                    （既定 .claude/tmp/cdev-loop-{timestamp}/）
├── state.jsonl              進行状態
├── g1c1/
│   ├── design/              /cdev:coding の設計ドキュメント
│   ├── coding-result.jsonl  /cdev:coding の結果
│   ├── review/              /creview:rounds のレビュードキュメントと最終レポート
│   └── rounds-result.jsonl  /creview:rounds の結果
├── g1c2/
│   ├── handoff.md           差し戻しの申し送り
│   └── ...
├── g1/
│   ├── postmortem.md        ポストモーテムの分析
│   └── postmortem.jsonl     ポストモーテムの判定
├── g2c1/
│   ├── handoff.md           グランドリセットの申し送り
│   └── ...
├── cleanup/
│   └── plan.jsonl           --cleanup の積み直しの計画
└── loop-summary.md          実行サマリー
```

- ディレクトリはメイン作業ツリーに置かれ、相対パスの `--output` はリポジトリのルートを基点に
  解決します。開始時に存在しないか空である必要があり、実行後も残ります。
- `state.jsonl` は、進行の位置、各サイクルの結果、ターニングポイント、差し戻し、`--cleanup` の
  結果を記録します。
  ループはステップごとにこれを更新し、セッションのコンテキストが圧縮された後はこれを読み直して
  位置を取り戻します。別のセッションで実行を再開する機能はありません。
- 終了時に書く `loop-summary.md` は、各サイクルの終了理由、差し戻し、ポストモーテムの判定と
  採用世代、ターニングポイントとその削除方法、警告、残ったワークツリーを記します。警告には、
  たとえば QA・ビルド・解釈テストの警告、`/cdev:coding` のライターが報告する設計やタスク
  からのコードの乖離、成果物ブランチの作成失敗があります。
  - `--cleanup` では、積み直したコミットとその件名、または積み直さなかった理由も記し、元の履歴が
    作業ブランチに残ること、最後より前のコミットはビルドもテストもしていないことを示します。

### 停止する場合

ループが止まってユーザーに報告するのは、次の場合に限ります。

- 開始時の確認に失敗した。たとえば、セッションがリポジトリのルートで開始されていない、要件を
  満たさない、ブランチ名が使われている、実行ディレクトリが空でない。このときはサマリーを
  書かずに終わります。
- `/cdev:coding` が異常終了した。結果を書かなかった、途中で止まった、ワークツリーを残した、
  のいずれかです。
- `/creview:rounds` がエラーで終わった。
- `/creview:rounds` がワークツリーを残した。未コミットの変更や初期化したサブモジュールが
  残った場合などで、次のフェーズが作業ブランチをチェックアウトできない。
- 作業ブランチかターニングポイントを作成できない、内側のスキルの後にセッションがリポジトリの
  ルートへ戻れない、または `state.jsonl` を書けないか正しい形にできない。

それ以外は、尋ねずに判断して続けます。エラーで止まったときは成果物ブランチを作りません。
それまでに作ったターニングポイントと作業ブランチは残り、報告は、止まったステップ、エラー、
最後の作業ブランチ、`loop-summary.md` を示します。

終了時の次の 2 つの失敗では、実行は止まりません。警告付きの正常終了になり、`loop-summary.md`
がその警告を記録します。

- `--cleanup` の積み直しが失敗した: 計画者の計画を受理できない（再起動は 1 回まで）、または
  `commit-plan.py` がコミットを作れない。このときは `--cleanup` なしと同じく、採用世代の
  作業ブランチの先頭に成果物ブランチを作ります。
- 成果物ブランチを作成できなかった。積み直していなければ、採用世代の作業ブランチ
  `{branch}-g{g}` が同じコミットを持ちます。積み直していれば、報告が積み直しの最後のコミットの
  SHA を示します。このコミットは作業ブランチと同じツリーを持ちますが、履歴は異なります。

### 要件とコスト

- `/cdev:coding` と `/creview:rounds` が要するものをすべて要します: バックグラウンドの
  サブエージェントと `SendMessage`、深さ 3 以上のサブエージェントのネスト起動
  （`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`）、信頼できるリポジトリ、リポジトリのルートで
  開始したセッション。creview プラグイン 0.22.0 以降も必要で、Claude Code が cdev の依存
  として一緒にインストールします。
- プロジェクトの configure・ビルド・テストが、ワークツリーに初期化したサブモジュールも
  `.gitignore` の対象外の未追跡ファイルも残さないこと。git はそのようなワークツリーの削除を
  拒み、内側のスキルがワークツリーを残すので、ループはそのフェーズの後に止まります。多くは
  最初のコーディングフェーズの後です。
- 1 回の実行は最大 `(1 + max_sendbacks) × max_generations` サイクルで、既定値では 9 です。
  各サイクルは、チーム結成から QA までの `/cdev:coding` と、最大 `--max-rounds` ラウンドの
  レビューを含み、差し戻しのたびに次のレビューの Round 1 が世代全体を見直します。
  `--pursuit` では世代数の上限まで実行が続きやすくなります。セッション内で起動する
  サブエージェントの総数と同時に実行中の数の上限は、[creview の README](../creview/README_ja.md)
  を参照してください。
- ターニングポイントは 1 サイクルあたり 2 本で、既定値では最大 18 本になります。
- `--cleanup` では、終了時に計画者のサブエージェントの起動が 1〜2 回増えます。
- メイン作業ツリーのソースは変更しません。その未コミットの変更は開始コミットに含まれず、実行の
  対象外となります。ループは開始時にその旨を示します。

## アーキテクト / コーダー / ライター / レビュアーエージェント

同梱エージェントに挙げるコメントとプロンプトの専門家を除き、このプラグインは専門の
レビュアーを同梱しません。`team-analysis`
タスクが**移植先プロジェクト**（`.claude/agents/`）→**ユーザー**（`~/.claude/agents/`）→
**プラグイン同梱**の順に、サブディレクトリを含めて再帰的（`**/*.md`）にエージェントを列挙し、
各エージェントの frontmatter の `name` / `description` を読み、**レビュアー**ロールに最適な
専門家を割り当てます（各レビュアーは producer のドメインを担当し、専門外の領域を 1 人に
兼任させません）。**アーキテクト・コーダー・ライターは常に `general-purpose` で起動します**
——一部の専門家エージェントがツールコールを誤整形して停止するため、かつ producer は
割り当てスコープとプロジェクト規約に従って作業し、ドメインの正しさは専門家レビュアーが
レビューで担保するためです。ドメインに一致する専門家が無い場合は `general-purpose` に
フォールバックします。設計セルの後のチームの再編成も、加えるレビュアーを同じエージェントの
プールから同じ規則で選びます。チーム結成、チームの再編成、または QA による修正担当の推定が
同梱エージェントを素の名前（例: `prompt-sensei`）で返し、その名前のエージェントが利用できない
場合、スキルは `cdev:{name}` で起動します。

## 同梱エージェントとサポートファイル

- `agents/dev-helper.md` — 機械的な teammate。チーム結成（スコープ確定 + アーキテクト・
  コーダー・ライター・レビュアーの選定）、設計後のチームの再編成（設計が追加・変更する
  ファイルのコーダーとライターへの割り当てと、要るコーダー / ライター / レビュアーの選定）、
  QA（プロジェクトのフォーマット / ビルド / テスト実行、失敗時の修正専門家の特定）、
  コミットの計画（変更ファイルを論理的な変更ごとのコミットに分ける）を担う。
- `agents/comment-sensei.md` — コードコメントの専門家 teammate。コーディング中に追加・
  変更されたコメントを `rules/comment.md` に照らしてレビュー・修正する。
- `agents/prompt-sensei.md` — AI 向けプロンプトの専門家 teammate。コーダーが変更した
  プロンプトファイルを `rules/prompt.md` に照らしてセルフチェック・修正・圧縮し、QA ゲートで
  解釈テストを実行する。チーム結成でプロンプトファイルのレビュアーに選ばれることもある。
- `agents/prompt-tester.md` — `prompt-sensei` が QA ゲートで起動する、文脈を持たない解釈
  テスト担当。Read・Glob・Grep のみを持ち、チーム結成の候補にはならない。
- `rules/` — `teammate.md`（teammate 共通ルール）、`agents-detection.md`、
  `build-format-detection.md`、`comment.md`、`review.md`、`document.md`、`prompt.md`
  （プロンプト規律）、`divergence.md`（設計に持ち込んではならない発散パターンと、
  コードセルでプロンプトファイルの過剰指定を防ぐ対処）、`commit-plan.md`（コミットの
  ステップと `/cdev:loop --cleanup` の計画者が変更をコミットに分ける基準、コミットの
  メッセージ、計画ファイルの形式）。
- `scripts/` — `fetch-diff.sh`（コーディング開始前のツリーを記録し、開始以降の差分を
  ドキュメントセルと QA のために取得）、`del-tmp.sh`（`.claude/tmp/` 配下の実行作業
  ディレクトリを削除。`--dry` では封じ込めチェックのみを行い、スキルはこのディレクトリの
  作成前にこれを実行する）、`check-jsonl.py`（teammate が、書き出した `.jsonl` の各行が
  1 つの JSON オブジェクトであることの検証に使用）、
  `lib/scratch-guard.py`（両者が共有する `.claude/tmp/` 封じ込めチェック。`python3` が必要 —
  動作要件参照）、`worktree.sh`（`--worktree` のワークツリーを作成・削除）、`restore.sh`
  （設計の復元リストのエントリをターニングポイントのコミットから作業ツリーに復元する。
  未追跡のファイルかローカル変更のある追跡ファイルを上書き・削除するか、エントリの外のパスを
  変えるエントリは拒否する。git のチェックアウトと同じく無視ファイルは上書きしうるため、
  `--worktree` の実行のワークツリーでだけ使う）、`commit-plan.py`（変更パスを列挙し、
  コミットの計画をそれに照らして検査し、`commit` で計画どおりのコミットを作業ツリーから作り、
  `build` で 2 つのコミットの間の変更を、ref・インデックス・作業ツリーのどれにも触れずに新しい
  コミットに積み直す）。スキルは
  `${CLAUDE_PLUGIN_ROOT}/scripts/...` 経由で呼び出し、teammate は
  変数 `{{plugin_root}}` で解決済みパスを受け取ります。

## ビルド / テスト検出

QA は `rules/build-format-detection.md` でプロジェクトのフォーマット / ビルド / テスト
コマンドを解決します。`build-format.md` 記述子（`.claude/rules/**/build-format.md`）を最
優先し、無ければ `CLAUDE.md`、次に `README.md` を参照します。いずれもワークフローを宣言
していない場合、QA は目視チェックのみを行い、`build-format.md` 記述子の追加を推奨する警告を
返します。

## 日本語マスタ（リポジトリ直下 `src/cdev/`）

日本語マスタはリポジトリ直下の `src/cdev/` にあり、本プラグインのツリーを 1 対 1 で
ミラーします（`src/cdev/skills/coding/SKILL.md` ↔ `cdev/skills/coding/SKILL.md` など）。
スキル名もプラグインと同一です。ここにある実稼働の英語ファイルは、そのマスタを翻訳して
生成されます。更新する際は `src/cdev/` 配下の日本語マスタを編集し、その後実稼働ファイルへ
パス書き換え（`${CLAUDE_PLUGIN_ROOT}` / `{{plugin_root}}`）を再適用します。
