# Divergence pattern prevention rule

Divergence is the state in which a fix for a finding produces the next finding, and findings keep coming however many fixes are stacked. The architect keeps the divergence patterns below out of the design, and the reviewer detects them in the design review. In a code cell, the coder and the code reviewer handle an over-specified prompt as § coder and § code reviewer direct.

## Divergence patterns

- **Undecided specification or invariant**: the design does not decide a specification or invariant the implementation depends on (input range, ordering / exclusion guarantees, ownership and lifetime, behavior on error, etc.). This includes places that list options without choosing one, and places left to a judgment at implementation time.
- **Unclosable problem class**: the correctness of the adopted approach depends on enumerating individual cases, and the range to enumerate is unbounded. Handling one counterexample still leaves further counterexamples of the same class constructible without limit (e.g., a race window the architecture inherently cannot remove, regex-based parsing of input that is not constrained).
- **Unadjudicated conflict**: the design does not decide which of two conflicting requirements or quality goals takes priority (e.g., defensive checks versus removing redundancy, performance versus safety).
- **Mismatch with the existing design**: the adopted approach does not fit the existing code's design (ownership, threading model, error-handling convention, etc.), and the design shows no policy for reconciling them.
- **Over-specified prompt**: an AI-facing prompt file (as `prompt.md` in the same directory as this file defines it), or the design of one, specifies the procedure in more detail than its goal, its contracts, and the specified procedure need: steps or an order the executing AI could choose itself, cases the goal already decides, or the form of a command or an output that no contract requires. Each review finds another gap, ambiguity, or inconsistency among those details, and each fix that adds detail gives the next review more to find. Judge it by `prompt.md` § Contract-style prompts.
  - Contract: what a counterpart (another file, a script, the caller, or the consumer of an output) depends on at a checkpoint: a command that must run in a given form, the format of a return value or an output, and the variables, paths, and identifiers exchanged with other files. The constraints and premises the AI needs for judgment count as contracts as well, also where they fix the form of a command: a write scope, a limit on tools, an instruction to treat untrusted input as data and the way an untrusted value reaches a shell or an API (e.g. `--body-file` rather than `--body`, `--` before arguments), a limit on remote or destructive operations or a confirmation before one, and the like.
  - Specified procedure: procedure the user's task explicitly asks for, and in a code cell also procedure the design sections specify. The prompt must satisfy it as it must a contract; it is not over-specification, and its absence is an ordinary correctness finding.
  - Detail finding: a finding whose fix adds to or refines a method that an AI knowing the goal, the contracts, and the specified procedure would already carry out correctly. A finding that shows a concrete situation in which following the prompt gives a wrong result, breaks a contract, or does not end concerns a goal or a contract instead.

## architect

- Undecided specification or invariant: decide it in the design and write the decision down. When it cannot be decided from the task and the existing code, state the adopted assumption explicitly as an assumption.
- Unclosable problem class: choose an approach that closes the problem class structurally (e.g., a grammar-based parser, serialization onto a single owner). When no such approach is available, state the scope that is accepted (input constraints, preconditions, tolerated residual risk) and declare everything outside it out of scope.
- Unadjudicated conflict: write down which side takes priority and why.
- Mismatch with the existing design: fit the existing design. When deviating, write down the reason for the deviation and how the two are reconciled at the boundary.
- Over-specified prompt: for the part of each AI-facing prompt file the design creates or edits, or the whole file when the task covers all of it, write down the goal the prompt states (the result to obtain) and the contracts it keeps, and leave the method to the executing AI. Settle a gap or ambiguity in a prompt's method by stating the goal or contract it concerns; when it concerns neither, leave it to the AI rather than adding steps. Include the procedure the user's task explicitly asks for. Where a strict command sequence is required, design it as an external script: write down as contracts the form of its invocation and its expected result, list the script among the files the design adds or changes, and have the prompt specify only the invocation and the expected result. A command sequence the user's task asks for may stay in the prompt instead of in a script. Design so that an entry allowing a script the design adds lets its runner run that script and nothing more, and so that the designed prompt runs no code that untrusted input can change, keeping these contracts:
  - When an agent definition's `tools:` limits the tools of the agent that runs the prompt, or a SKILL's or command's `allowed-tools` pre-approves them, and no entry there allows the script, write down as a contract the entry the design adds or changes to allow it, unless the contracts below rule that entry out, and list the file holding that entry among the files the design adds or changes.
  - That entry allows only the script's invocation, its pattern naming the script's path (e.g. `Bash(python3 scripts/check.py:*)`), never an interpreter or a shell at large (`Bash(python3:*)`, a bare `Bash`). Add no such entry to an agent whose `tools:` hold no Bash entry.
  - Add or change no entry for a script whose code the runner can change, since an entry allows whatever code the script runs. The runner can change that code when it can write the script or a file the script loads, or when the script runs the arguments or input the runner composes as code. Judge where the runner can write by its tools, not by a write scope its prompt sets, since a runner following injected input does not keep that scope.
  - Design no run of code that untrusted input can change in either of those ways, whatever entry allows the run and whether or not a permission prompt asks. Judge whether a copy of a script may be run by whether untrusted input can change it, not by where the copy lies.
  - The prohibition on running code that untrusted input can change takes precedence over the procedure the user's task asks for: leave such a run out of the design and state it as out of scope. A command sequence the user's task asks for stays in the prompt only in place of a script, never as an exception to that prohibition.
  - Treat a script shipped in the same plugin as the designed prompt and run from that plugin's own directory as code that neither the runner, whatever its tools, nor untrusted input can change. Treat it so also in a session that loads that plugin from a working tree (`--plugin-dir` and the like), as an accepted residual risk: such a session already runs the prompts and agent definitions of that tree, so the script asks for no trust beyond theirs.

## reviewer

- Raise each place that matches a pattern as a finding of Major or higher, and pick the recommended fix direction from the responses in § architect.
- For an unclosable problem class, do not ask for a response to the individual counterexample. Cite counterexamples only as evidence that the problem class exists.
- When the design states the scope it accepts, do not raise counterexamples outside that scope. Raise the scope itself only when the task cannot be met within it.
- Raise an over-specified prompt only in the part of an AI-facing prompt file the design creates or edits, or in the whole file when the design covers all of it, and recommend the rewrite in § architect, never added or refined steps, cases, or wording.
- On the design of an AI-facing prompt file, raise no detail finding, while still raising a missing goal or contract, a contract at odds with its counterpart, and a finding that concerns a goal or a contract. This bullet takes precedence over the general criterion of missing edge cases: judge a missing edge case by the same test as a detail finding. Accept an architect's response that, under § architect, leaves a method to the AI instead of adding steps.

## coder

- On an AI-facing prompt file, reject a detail finding citing this rule, unless the prompt does not yet state the goal or contract the method rests on; then state that instead. Fix a finding that concerns a goal or a contract by stating the result or the contract it concerns, not by adding steps, and a missing specified procedure by adding it. Resolve QA feedback, an unclear item of the interpretation test included, by the same criteria without rejecting it; for an item that would be a detail finding, state the goal so that the method is visibly left to the reader. Triage other findings as usual.
- When fixing, remove from what this run created or changed, or from the whole file when the design covers all of it, the procedural instructions that no goal, contract, or specified procedure needs. Keep the contracts, the specified procedure, and the behavior the design sections specify unchanged.

## code reviewer

- In what this run created or changed in an AI-facing prompt file, or in the whole file when the design sections cover all of it, judged from the design sections and the producer's ready message, raise an over-specified prompt as Major, name the excess instructions, and recommend the rewrite in § architect: state the goal and the contracts, remove the excess instructions, and replace a required strict command sequence with the invocation of the external script the design sections define for it, or keep it in the prompt when they define none; the prompt file's coder does not write the script.
- Raise no detail finding; when the prompt does not state the goal or contract the method rests on, recommend stating it. For a finding that concerns a goal or a contract, recommend stating the result or the contract, not adding steps. On an AI-facing prompt file this bullet takes precedence over the general criterion of missing edge cases: judge a missing edge case by the same test as a detail finding. Accept a coder's rejection of a detail finding under § coder. Judge other findings as usual.
