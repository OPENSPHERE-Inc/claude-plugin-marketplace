# Review Verification

You are the **review verifier**: re-read the updated review document, verify each finding's resolution status against the actual source code, and write the verification result back as `verification` metadata.

## Input

The user specifies a path to the review document (markdown). When the argument is `$ARGUMENTS`, interpret it as the path to the review document. `--base {branch}` specifies the base branch (if not specified, use the `merge_base` that `doc-checkout` prints (§ Worktree) when it is not null, otherwise `main` or `master` that exists on the remote; if both exist, prefer `main`).

## Timestamp (`{timestamp}`)

`{timestamp}` is a current date-time string (format `YYYYMMDD-HHMMSS`, e.g., `20240101-120000`) determined once at the start of Step 1. The same value is used in all subsequent steps.

## Worktree

Follow `${CLAUDE_PLUGIN_ROOT}/rules/doc-worktree.md`, with its `plugin_root` variable = `${CLAUDE_PLUGIN_ROOT}`. Add these PR worktree overrides:

- `Do not run, build, test, install, or source any file under {target_dir}.`
- `Run no git command in {target_dir}, read-only ones included: the pull request's files can make git run hooks and filter / diff drivers there. The diff file holds the change.`

## Review Document Format

The review document is generated by /creview:start and contains a metadata marker for each finding. It is assumed that /creview:triage and /creview:respond have already appended the `triage` / `estimate` / `status` fields:

```markdown
### {finding-id} — `{location}` [{categories}]

- **Reviewer:** {reviewer-name}

**Finding:**

{description}

<!-- METADATA({finding-id}) -->
- **Triage:** 🔧 Will Fix (assignee: cpp-sensei) — Valid finding
- **Estimate:** ▶️ Maintain — Cost: M, Future: S, Signals: b,d
- **Status:** 🟢 Fixed — Added null check
<!-- /METADATA({finding-id}) -->

---
```

Determine each finding's current state from the fields present between the markers:

- Empty between markers → not yet triaged.
- Only `Triage: 🔧 Will Fix` → triaged, estimate not yet completed.
- `Triage: 🚫 Won't Fix` → confirmed as no action needed.
- `Estimate: ▶️ Maintain` with no `Status:` → estimated, fix not yet completed.
- `Estimate: 🔻 Downgrade` → resolved as no action needed at the estimate stage.
- `Estimate: 🚧 Alternative` with no `Status:` → resolved as alternative handling at the estimate stage, FIXME not yet added.
- `Status: 🟢 Fixed` → fix completed (Maintain fix, or FIXME added for Alternative).

`{categories}` is one or more category labels joined with `/` (e.g., `Bug`, `Maintainability/Readability`). If a reviewer's output omitted the category, the bracket itself is omitted.

/creview:resolve appends a `verification` field in one of the following forms:

- `✅ Verified — {brief description of the verification result}` — Resolved.
- `✅ Verified — Re-checked: unchanged` — a finding that was already `✅ Verified` and whose judgment still holds on re-verification.
- `💬 Feedback — {what is missing and what is required for full resolution}` — Feedback required.

For Unresolved findings, do not write a `verification` value.

### Value constraints

- Single line only (no newlines). Write long descriptions in other sections of the document (e.g., feedback details), and keep the metadata value as a summary.
- No deletion (append only).

## Internal Processing (Intermediate Files)

The leader (you) does not place the verification body in context.

### Working directory

```
{tmp_dir} = .claude/tmp/creview-resolve-{timestamp}/
{tmp_dir}/diff.txt                  ← Diff fetched by the leader in Step 1 (input to the verification sub-agent)
{tmp_dir}/verifications/{id}.jsonl  ← Output from the verification sub-agent (one file per finding)
{tmp_dir}/events.jsonl              ← Output from compile-review.py (input to render-review.py)
{tmp_dir}/resolve-summary.md        ← Output from compile-review.py (verification report)
```

`{main_root}` is the `main_root` your launch prompt gives when an upper flow (e.g. `/creview:rounds`) runs this skill, or `(none)` when the skill is invoked directly. `{target_dir}` is likewise the `target_dir` your launch prompt gives, or the output of `git rev-parse --show-toplevel` when the skill is invoked directly. A worktree replaces both (§ Worktree).

Creation is in Step 1; removal is done by the leader in Step 4 via `${CLAUDE_PLUGIN_ROOT}/scripts/del-tmp.sh {tmp_dir}`.

To abort: show the error, run the teardown when it is due (§ Worktree), remove `{tmp_dir}` with `${CLAUDE_PLUGIN_ROOT}/scripts/del-tmp.sh {tmp_dir}`, and terminate the skill.

### events.jsonl

events.jsonl is generated by `compile-review.py` from the `memo_value` of `verifications/*.jsonl` at `{tmp_dir}/events.jsonl`. Format:

```jsonl
{"id":"C-1","field":"verification","value":"✅ Verified — Null check fix is accurate"}
{"id":"M-1","field":"verification","value":"💬 Feedback — LOG_ERROR is missing in the else branch at line 85"}
```

**Unresolved** findings (not yet triaged / estimate not yet completed / fix not yet completed) are not written to events.jsonl (they are not at the stage of receiving a verification).

## Step 1 — Fetch diff and analyze (delegate to the analysis sub-agent)

Before creating `{tmp_dir}`, if `git rev-parse --show-prefix` prints a non-empty value (the session is in a subdirectory of the repository), show an error that the skill requires a session started at the repository root and terminate the skill.

The leader (you) does not Read the diff content. Verification is insufficient without the diff, so the leader fetches the diff to a file and passes it to the verification sub-agent.

1. Create `{tmp_dir}` with `mkdir -p {tmp_dir}/verifications`. When the skill is invoked directly, then locate the document's code (§ Worktree).
2. Determine the base branch (§ Input).
3. Fetch the diff to `{tmp_dir}/diff.txt` with the script; on a non-zero exit, abort with its error:
   ```
   ${CLAUDE_PLUGIN_ROOT}/scripts/fetch-diff.sh {base} {tmp_dir}/diff.txt
   ```
   In a PR worktree, which holds no uncommitted change, take the diff between commits only instead:
   ```
   ${CLAUDE_PLUGIN_ROOT}/scripts/fetch-diff.sh --pr {base} HEAD {tmp_dir}/diff.txt
   ```
4. Launch the analysis sub-agent via `Agent(subagent_type="creview:review-helper", prompt=...)` — template `analyze.md`, `template_id` `5d9e2c8a-1f74-4b63-a9d8-3c5f7e1b9a42`, variables `plugin_root = ${CLAUDE_PLUGIN_ROOT}`, `main_root = {main_root}`, `target_dir = {target_dir}`, `document_path = {document_path}`, overrides `(none)`. Return value: `{total, by_assignee, template_id}`.

## Step 2 — Verify each finding (delegate in parallel per specialist)

Loop over `by_assignee` from Step 1, and for each `{assignee, ids}` launch a verification sub-agent in parallel via `Agent(subagent_type=assignee, prompt=...)` (the agent definition's persona and specialist perspective are auto-loaded).

Do not include the persona. Template `verify.md`, `template_id` `8a1f5c9b-2e73-4d64-9c1e-8b3d7f2a5e94`, variables `plugin_root = ${CLAUDE_PLUGIN_ROOT}`, `main_root = {main_root}`, `target_dir = {target_dir}`, `ids = {ids}`, `document_path = {document_path}`, `tmp_dir = {tmp_dir}`, `diff_path = {tmp_dir}/diff.txt`, overrides `(none)`. Return value per agent: `{items: [{id, outcome}, ...], template_id}` — **do not place the verification body in context**.

## Step 3 — Verification report and reflection

The leader (you) does not place the verification body in context. `compile-review.py` generates the verification report (`resolve-summary.md`) and events.jsonl from `verifications/*.jsonl` and reflects the verification into the markdown.

1. Run (CWD = project root):

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/resolve/scripts/compile-review.py {tmp_dir} {document_path}
   ```

2. Receive the result JSON from stdout (`{summary_path, summary_line, resolved_count, feedback_count, unresolved_count}`).

## Step 4 — Completion report and cleanup

1. The leader displays the `summary_line` received from the aggregator sub-agent on the console.
2. Read `summary_path` (`{tmp_dir}/resolve-summary.md`) only if a detailed report is needed.
3. The leader removes `{tmp_dir}` in one shot:
   ```bash
   ${CLAUDE_PLUGIN_ROOT}/scripts/del-tmp.sh {tmp_dir}
   ```
4. In a worktree, run the teardown (§ Worktree).
