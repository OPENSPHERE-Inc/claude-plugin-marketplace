# creview

*[English README](README.md)*

Claude Code 向けのマルチエージェント並列コードレビューワークフロー。

## スキル

| コマンド | 由来 | 目的 |
|---------|-----------|---------|
| `/creview:start` | `parallel-review` | ローカルの変更または GitHub プルリクエストの並列コードレビューを実行し、メタデータマーカー付きのレビュードキュメントを生成する。 |
| `/creview:triage` | `review-respond`（トリアージ + 見積） | レビュードキュメントまたは GitHub プルリクエストのコメントの指摘をトリアージ・見積し、`triage` / `estimate` をドキュメントへ永続化する。 |
| `/creview:respond` | `review-respond`（修正） | Will-Fix / Maintain / Alternative の指摘を修正し、ビルドを検証し、`status` を永続化する。 |
| `/creview:resolve` | `review-resolve` | レビュードキュメントまたは GitHub プルリクエストのコメントの指摘の解決状況をソースに照らして検証し、`verification` を永続化する。 |
| `/creview:rounds` | `review-rounds` | start → triage → respond → resolve を複数ラウンドにわたって自動反復する。 |

どのコマンドも、`--worktree` の有無にかかわらずリポジトリルートで起動した
セッションを必要とし、リポジトリのサブディレクトリから起動した場合は
エラーで終了します。

`review-respond` は 2 つのスキルに分割されました。先に `/creview:triage <doc>`
を実行し、ドキュメントに永続化された判定を確認してから `/creview:respond <doc>`
を実行します。どちらのスキルにも確認プロンプトはありません — 分割そのものが
レビューゲートです。`/creview:respond` は `--commit` オプションを保持します。

レビュードキュメントは、ローカルの変更のレビューでも、レビューを実行した
ブランチを `- **Branch:** {branch}` のヘッダー箇条書きに記録します。単独で
実行した `/creview:triage`、`/creview:respond`、`/creview:resolve` は、その
ブランチがチェックアウトされていなければそのブランチの一時的なワークツリーで
作業し、`/creview:respond` はそこで修正をそのブランチへコミットします。
ワークツリーにはそのブランチのコミット済みの内容しかないため、未コミットの
変更を含めてレビューした場合は、先にその変更をコミットするか、そのブランチを
チェックアウトし変更を作業ツリーに残したまま実行してください。ヘッダー
箇条書きの詳細は、後述のプルリクエストのレビューの説明の後で述べます。

`/creview:start` には `--adversarial` オプション（デフォルト OFF）があり、
Critical / Major の指摘に具体的な失敗シナリオを求める敵対的モードで
レビュアーを実行します（`/creview:rounds` も同じフラグを受け取り、
`/creview:start` へそのまま渡します）。`/creview:triage` の敵対的トリアージは
常時有効で、指摘を最大 8 件ずつのバッチに分割し、トリアージサブエージェントの
一次判定にバッチごとの 3 体の反証サブエージェントがそれぞれ独立に可能な範囲で
反対の論を立て、裁定サブエージェントが最終判定を決めます。一次判定が覆るのは、
担当バッチの 3 体のうち 2 体以上が反転を支持し、かつ裁定サブエージェントが
その根拠となる事実を確認できた場合に限られます。

`/creview:start` は 1 レビュアーが担当する差分量にも上限を設けます。変更が
800 行または 20 ファイルを超える場合、scope-analysis サブエージェントが変更
ファイルを最大 8 個の凝集したレビュースコープ（1 スコープあたり変更 400 行 /
10 ファイルまで）に分割し、スコープごとにレビュアーを選定します。数件の指摘を
出した時点で探索を打ち切るレビュアーによる局所的なサンプリングではなく、大きな
変更をスライス単位でレビューできます。これを下回る変更は単一スコープのままです。

バイナリファイル、モード変更、空ファイルの追加・削除のように追加・削除行を
持たない変更も含め、変更されたすべてのファイルをレビュアーに割り当てます。
変更されたファイルが 1 つもない場合はレビュアーを起動せず、レビュードキュメントは
重要度のセクションを持たないヘッダーだけになります。
バイナリファイルについて、差分は変更されたことだけを示します。scope-analysis
サブエージェントは、そのファイルの拡張子だけでなく、ソース中でそのファイルを
使う箇所からもレビュアーを選びます。各レビュアーはその文脈と自身の観点から、
レビューが必要か（例: 更新した画像が Web ページのレイアウトを変えるか、想定 DPI
に対して解像度が足りるか）を判断し、必要ならファイルを読み込みます。レビュアーは
画像なら中身を確認できますが、フォントやアーカイブなどほかの形式のバイナリ
ファイルは、使う箇所からのみ判断します。

先頭 8,000 バイト以内に NUL バイトを含むテキストファイルや、`.gitattributes` で
`binary` または `-diff` が指定されたパスも、git はバイナリとして扱い、差分は
その中身を示しません。レビュアーはそうしたテキストファイルを、使う箇所に
かかわらず全体を読み込み、テキストとしてレビューします。変更されたファイル
では差分が変更行を示さないため、変更箇所を特定できなかったことも指摘として
報告します。追加・変更を問わず、ファイル全体を表示できなかった場合も同じ
指摘を報告します。

`/creview:start` はレビュー対象として GitHub プルリクエストの URL
（`https://{host}/{owner}/{repo}/pull/{number}`）も受け取り、その場合は
そのプルリクエスト、すなわちマージベースから head コミットまでの差分を
レビューします。プルリクエストは open で、そのホスト上のリポジトリが現在の
クローンのリモートである必要があり、GitHub CLI（`gh`）がそのホストに認証済みである必要が
あります。プルリクエストのレビューには Git 2.41 以降が必要で、それより古い Git では
エラーで終了します。`--base` と `--range` はプルリクエストの URL と併用できません。
差分は、リネーム検出なしで、マージベースの `.gitattributes` に従い、サブモジュールが
指すコミットの差し替えをすべて含めて取得するため、類似度 100% のリネームも
プルリクエストの `.gitmodules` や `.gitattributes` も、変更をレビュアーから
隠せません。サブモジュールについては差し替え前後のコミットだけを示し、
サブモジュール内のファイルの変更は含みません。差分がバイナリとして示す
テキストファイルは、チェックアウトしたプルリクエストから読み込みます。

- HEAD がプルリクエストの head コミットである場合は、作業ツリーをそのまま
  レビューします。追跡ファイルに未コミットの変更がある場合はエラーで終了します。
- それ以外の場合は、`.claude/worktrees/` 配下の一時ワークツリーに head コミットを
  detached でチェックアウトします。その際 git フックと git 設定のフィルター
  ドライバーは無効化され、Git LFS の smudge は行わず、シンボリックリンクは
  リンク先のパスを中身とする通常ファイルとして展開されます。ワークツリーは
  実行の終了時に、同じくフックとフィルタードライバーを無効にして、中身ごと
  削除されます。このワークツリーはその実行専用で、`/creview:rounds --worktree` とは無関係です。
  - レビュードキュメントと作業用ディレクトリはメイン作業ツリーの
    `.claude/tmp/` に置かれ、プロジェクトの `.claude/agents/` はメイン作業
    ツリーから読み込まれます。
  - チェックアウトからはエージェントファイルを除外します。大文字小文字を問わず、
    どの階層でも、`CLAUDE.md`、`CLAUDE.local.md`、`AGENTS.md`、`.mcp.json`、
    `.claude` という名前のファイルとディレクトリすべてが対象です。サブエージェントが
    ワークツリーで作業すると、Claude Code や他のエージェントがそれらを指示・
    スキル・設定として読み込みうるためです。
    - レビュアーは、それらへのプルリクエストの変更を差分でのみ確認します。
      差分がそのいずれかをバイナリとしてしか示さない場合は、中身をレビュー
      できなかったことを指摘として報告します。
    - `--trust` を指定すると、それらもチェックアウトします。
    - プルリクエストのエージェント設定を、ファイルのある状態でレビューするには、
      `--trust` を指定するか、作業ツリーに head コミットをチェックアウトして
      その場でレビューし、いずれもサンドボックス内で実行してください。

コードのレビュアーと並行して、同梱の `pr-description-reviewer` がもう 1 体
動き、プルリクエストのタイトル・本文と CI 結果に照らして変更を確認します。

- 変更が裏付けない主張、レビュアーに必要なのに本文が書いていない情報、
  未完了のタスク項目、失敗したチェックを指摘します。失敗の原因は、失敗した
  GitHub Actions ジョブのログからたどります。
- プルリクエストのコメントとレビューは文脈を理解するための参照情報として
  読むだけで、レビュー対象にはしません。
- すべての指摘を変更されたコードの行にアンカーし、根拠とした本文の記述や
  CI 出力を引用します。差分のどこにも関わらない主張や、原因が変更の外にある
  チェックの失敗など、変更行に結び付かない問題は報告しません。
- Read / Glob / Grep / Write だけで動き、シェルとネットワークへの
  アクセスを持ちません。

すべての creview サブエージェントに、プルリクエストのテキスト（タイトル・本文・
コメント・CI 出力・コミットメッセージ・ファイルに追加または変更した行）と、
レビュードキュメント内のその引用をデータとして扱い、GitHub やその他のリモートを
一切変更しないよう指示します。レビュードキュメントに対して `/creview:triage`、
`/creview:respond`、`/creview:resolve` を個別に実行した場合のサブエージェントも
同様です。ワークツリーでのレビューでは、チェックアウトしたファイル（`--trust` で
チェックアウトしたエージェントファイルを含む）もデータとして扱い、どれも実行せず、
ワークツリーで git コマンドを実行しないよう指示します。これは指示であって
強制ではありません。信頼できないプルリクエストでは、環境側（サンドボックス、
フック、権限ルール）の対策も併用してください。

ワークツリーでのレビュー中と、`/creview:triage`、`/creview:respond`、
`/creview:resolve` がプルリクエストのワークツリー（後述）で作業する間は、
セッションの作業ディレクトリがワークツリーになります。Claude Code のフック（サブエージェントのツール呼び出しでも
発火します）とステータスラインのコマンドはそこで実行されます。そのため、
それらが `npm run lint`、`./scripts/check.sh`、`git status` のように現在
ディレクトリを基準に実行するコマンドは、上記の保護なしにプルリクエストの
ファイルに対して動きます。信頼できないプルリクエストでは、そうしたコマンドを
無効にするか、`$CLAUDE_PROJECT_DIR` や絶対パスを基準に書いてください。
ワークツリーはプロジェクトの `.claude/worktrees/` の下にあるため、テストランナーや
`.` を対象にしたフォーマッターのようにプロジェクト全体を走査するコマンドでは、
そのディレクトリも対象から外してください。

レビュードキュメントは、`- **PR:** {url} (head {head_sha}, base {merge_base})`
形式のヘッダー箇条書きでプルリクエストを、`- **Branch:** {branch}` の箇条書きで
レビューを実行したブランチを記録します。ワークツリーでのレビューは detached HEAD
で実行するため、ブランチを記録しません。コミット範囲や、レビュー対象として
指定したブランチのうち、HEAD 以外のコミットで終わるもののレビューも同様です。
文字・数字・`_`・`.`・`/`・`+`・`@`・`-` 以外の文字を
名前に含むブランチは記録しません。`- **Trust:** on` または `off` の箇条書きは、レビューしたツリーにエージェントファイルがあったかを記録します。
その場でのレビューと `--trust` を指定したワークツリーでのレビューでは `on`、
`--trust` なしのワークツリーでのレビューでは `off` です。単独で実行した
`/creview:triage`、`/creview:respond`、`/creview:resolve` は、PR と Branch の
箇条書きからドキュメントのコードの場所を判断します。

- Branch の箇条書きがあれば、そのブランチがチェックアウトされているときは
  その場で、そうでなければ `.claude/worktrees/` 配下に作る一時的な
  ワークツリーでそのローカルブランチを対象に作業します。
  - その名前のローカルブランチがない場合（ブランチを削除した後や、別の
    クローンでレビューした場合など）はエラーで終了します。リモートのブランチ
    などからブランチを作り直してから、もう一度実行してください。
- PR の箇条書きだけがあれば、HEAD が head コミットを含むときはその場で、
  そうでなければ head コミットの一時的なワークツリーで作業します。
  - ワークツリーを作る場合は、プルリクエストがオープンのままで、head コミットが
    レビュー時と同じである必要があります（`gh` で確認します）。更新された
    プルリクエストはレビューし直してください。
- どちらもなければ（detached HEAD でのレビューや、HEAD 以外のコミットで終わる
  コミット範囲やブランチのレビューなど）、現在の作業ツリーで作業します。
  レビューしたコードを先にチェックアウトしてから実行してください。

PR の箇条書きを持つドキュメントのワークツリーはプルリクエストのコードを保持し、
ワークツリーでのレビューと同じくチェックアウトします。git フックとフィルター
ドライバーを無効にし、Git LFS の smudge をスキップし、シンボリックリンクを
通常ファイルとして扱い、Trust の箇条書きが `on` でない限りエージェント
ファイルを除外します。ドキュメントに対して実行する場合、3 つのスキルは
`--trust` を受け付けません。Trust の
箇条書きに従い、レビュー時と同じファイルで作業します。Trust の箇条書きが
ないドキュメントは `off` として扱います。エージェントファイルを含めて作業
するには、`--trust` を指定してレビューし直してください。サブエージェントには
ワークツリーでのレビューのサブエージェントと同じ指示を与えますが、コードを
修正・ビルド・テストする `/creview:respond` には、ファイルを実行しないことと
git を使わないことを指示しません。`/creview:respond` は、その場で実行する場合と
同様に、下に挙げる経路のうちチェックアウト自体を除く git とビルドの経路で
プルリクエストのコードを実行します。自身の git コマンド（`git status` や
`git commit` など）がそこに挙げたフック・フィルタードライバー・`core.fsmonitor`
を実行し、ビルドとテストがプルリクエストのビルドスクリプトとテストを実行します。
フォーマット・ビルド・テストのコマンドは、プルリクエストのファイルではなく
メイン作業ツリーの `build-format.md`・`CLAUDE.md`・`README.md` から取ります。

ワークツリーでは、`/creview:respond` は `--commit` を有効にします。PR の
箇条書きだけを持つドキュメントでは、ローカルブランチ `creview-pr-{number}` に
コミットします。このブランチは head コミットに作成し、すでにそこを指している
場合はそのまま使います。そのブランチを Branch の箇条書きとして記録するため、
以降の実行は修正後のコードを対象にします。ブランチをプルリクエストへ push
するのは利用者に任されます。同じドキュメントに対してブランチ上のその場で
実行した場合も、そのブランチを同様に記録します。Trust が `off` の場合、除外した
エージェントファイルの修正を要する指摘は修正せず、サマリーに理由とともに
示します。

終了時にワークツリーは削除され、ブランチは残ります。未コミットの変更が
残ったワークツリーは削除せず、そのパスを報告します。PR の箇条書きを持つ
ドキュメントのワークツリーを残すのは `/creview:respond` だけです。
コードを変更しない `/creview:triage` と `/creview:resolve` は、
そのワークツリーを変更の有無を確かめずに中身ごと削除します。
`/creview:respond` がそのワークツリーを削除する際は、プルリクエストで
シンボリックリンクであるファイル（ワークツリーでは通常ファイル）への変更も、
`git status` には現れませんが未コミットの変更として扱います。
そうしたファイルを検査できない場合（Windows で、パスが UTF-8 でないか
MAX_PATH を超える場合）もワークツリーを残します。エラーには
それらのファイルを示します。このワークツリーは後述の
`/creview:rounds --worktree` のワークツリーと同じく新規チェックアウトで、
gitignore 対象の依存物・仮想環境・ビルドディレクトリ・`.env` やサブモジュールの
中身がないため、`/creview:respond` のビルドとテストはそれらなしで通る
必要があります。サブモジュールを初期化したワークツリーも git が削除を拒否する
ため、同様に残してパスを報告します。その場合はエラーが示すとおり、ワークツリーと
そのサブモジュールに残すべき変更やコミットがないことを確かめてから
`git worktree remove --force -- <パス>` で削除してください。レビュードキュメント、
作業用ディレクトリ、プロジェクトの `.claude/agents/` と `.claude/rules/` は
メイン作業ツリーのものを使います。`/creview:rounds --worktree` が残した
ワークツリーのように、別のワークツリーでチェックアウト中のブランチは
チェックアウトできません。そのワークツリーのルートでセッションを開始して
スキルを実行してください。ただし、3 つのスキルが未コミットの変更または初期化した
サブモジュールのために残した `.claude/worktrees/` 配下のワークツリーは例外です。
変更をコミットまたは破棄し、エラーが示す `gh-pr.py remove` のコマンドで
（削除を拒否した場合はそのコマンドのエラーに従って）削除してから、スキルを
再実行してください。PR の箇条書きを持つドキュメントのワークツリーには、上の
どちらの回復手順も当てはまりません。このワークツリーはプルリクエストのコードを
保持し、その中で実行した git はプルリクエストのフックやフィルターを実行しうる
ためです。どの理由で残ったワークツリーでも、その中では git を実行しないでください。
残すものを外へ写してから、メイン作業ツリーで
`git worktree remove --force -- <パス>` を実行して削除してください。
creview が追加したプルリクエストのワークツリーで開始したセッション
では、3 つのスキルは実行を拒否します。`/creview:rounds` から実行された 3 つのスキルは
ワークツリーを作らず、ラウンドの作業場所で作業します。

作業ツリーでのチェックアウトには、ワークツリーでのレビューが備える保護がなく、
プルリクエストのコードが、たとえば次の経路で実行される可能性があります。

- git はチェックアウトの時点からフックとフィルタードライバーを実行します。
  - `core.hooksPath` が相対パス（`.husky/_`、`.githooks` など）の場合、フックは
    プルリクエストの tree のものになり、チェックアウトがその `post-checkout`
    フックを、`/creview:respond --commit` が `pre-commit` フックを実行します。
  - `.git/hooks/` に導入したフックマネージャー（pre-commit、lefthook、Husky v4
    など）はプルリクエストの tree の設定ファイル（`.pre-commit-config.yaml`、
    `lefthook.yml`、`package.json` など）を読むため、`core.hooksPath` がなくても、
    フックはプルリクエストがそこに書いたコマンドを実行します。
  - `core.fsmonitor` が相対パスの場合、チェックアウトや `git status` などの
    git コマンドがプルリクエスト版のそのスクリプトを実行します。
  - どのフィルターが実行されるかはプルリクエストの `.gitattributes` が決めます。
- Claude Code がプルリクエストの `CLAUDE.md`、`CLAUDE.local.md`、`AGENTS.md`、
  `.mcp.json`、`.claude/**` と、それらが `@` 参照で取り込むファイルを指示・
  スキル・設定として読み込む可能性があります。
- `/creview:respond` はフォーマット・ビルド・テストのコマンドを実行し、それを
  通じてプルリクエストのビルドスクリプトやテストを実行します。
  - `build-format.md` がない場合、そのコマンドはチェックアウトした `CLAUDE.md`
    または `README.md` から導きます。

creview は、実行する前に利用者がリポジトリとプルリクエストを確認し、
信頼していることを前提とします。上記の経路と、ワークツリーでのレビューが
備える保護は、その判断を補助するものにすぎず、プルリクエストのコードや指示が
作用するすべての経路を挙げるものではありません。ネットワークから取得したリポジトリやプルリクエストの安全を
保証することもできません。エージェントの安全はサンドボックスや権限ルールなど
利用者の環境で担保し、信頼できないプルリクエストのチェックアウトと
`/creview:respond` の実行はサンドボックス内でのみ行ってください。

`/creview:triage` と `/creview:resolve` は、レビュードキュメントの代わりに
GitHub プルリクエストの URL も受け付けます。まずプルリクエストのコメントから
レビュードキュメントを編纂し、そのドキュメントに対して通常どおり動作します。
プルリクエストが open で、そのリポジトリが現在のクローンのリモートであり、
`gh` が認証済みで、HEAD が head コミットの場合は追跡ファイルに未コミットの変更が
ないことが必要です。Git 2.41 以降が必要なのは、プルリクエストのワークツリーで
動作する `/creview:resolve` だけです。それより古い Git では、コメントの編纂を
終えた後にエラーで止まります。`--base` は URL と併用できません。ドキュメントの
Trust の箇条書きは、`--trust` を指定したとき、または HEAD が head コミットで
その場で実行したときに `on`、それ以外では `off` になります。スキルがその
ドキュメント用に作るワークツリーがエージェントファイルを含むのは、`on` の
場合だけです。

- 同梱の `pr-comment-compiler` が、インラインレビューコメント、レビュー本文、
  会話のコメントのうち、コードの問題を指摘するものや変更を求めるものを
  指摘にします。
  - 承認、問題を述べない質問、CI やボットの状況報告は除外します。
  - 各指摘をチャットの言語で書き直し、コメントが述べる影響から重大度を
    決めます。
  - 問題は修正済みだと述べる返信は、検証されていない主張として指摘内に
    残します。
  - Read と Write のみで動き、シェルとネットワークへのアクセスを持ちません。
- `/creview:triage` は GitHub で解決済みとされたスレッドを編纂者が読む前に除外し、
  その件数を報告します。
  - スレッドはプルリクエストの作成者も解決済みにできますが、同じ URL を
    `/creview:resolve` に渡すと、それらのスレッドをコードと照合できます。
- `/creview:resolve` はそれらのスレッドも含め、トリアージや修正を経ていなくても
  すべての指摘をコードと照合します。
  - コードにその問題がなければ `✅ Verified`、まだある場合や、指摘が述べるコードを
    特定できない場合、指摘から問題の有無を判断できない場合は `💬 Feedback` とします。
  - `💬 Feedback` の指摘に対応するには、そのドキュメントに対して
    `/creview:triage` を実行してください。
- HEAD が head コミットを含むものの head コミットそのものではない場合、スキルは
  プルリクエストにないコミットや未コミットの変更を含み得るローカルのコードに
  対して動作し、その旨を実行結果で報告します。
- コメントは種類ごとに最大 10,000 件まですべて編纂し、それを超える場合は
  実行結果で報告します。
  - コメントはレビュースレッドを分割せず、約 40,000 文字ごとのバッチに分けます。
    - バッチごとに編纂者が読むため、コメントの多いプルリクエストではサブエージェントの
      数が増えます。
  - スクリプト `compile-pr-comments.py` が、編纂者の抽出結果からドキュメントを
    生成します。
    - バッチ内の重複は統合します。
    - 2 つのバッチにまたがる同じ指摘は 2 件のまま残り、`/creview:triage` の判定も
      `/creview:resolve` の検証も別々に行うので、どちらも修正対象になりえます。
- ドキュメントは `.claude/tmp/creview-triage-{timestamp}.md` または
  `.claude/tmp/creview-resolve-{timestamp}.md` に書き出され、プルリクエストの
  レビューのヘッダー箇条書きと `- **Source:** pr-comments` の箇条書きを持ちます。
  - コメントに指摘がない場合は、ドキュメントを作らずに終了します。
- プルリクエストにコメントできる人は誰でも、これらの指摘にテキストを入れられます。
  - 信頼できないプルリクエストではとりわけ、`/creview:respond` を実行する前に
    永続化された判定を確認してください。
  - `/creview:triage` は各指摘の判定と修正計画をコードから導き、コメント投稿者の提案
    からはコード自体が求めるものだけを採ります。
  - `/creview:respond` は修正計画を実行し、計画を判定し直しません。
    - `/creview:triage` を通った提案は、外部スクリプトの実行、チェックの削除、
      依存の置き換えなどであっても適用されます。
    - 残る歯止めは、永続化された判定を利用者が確認することだけです。

`/creview:triage` と `/creview:respond` には `--adr` オプション
（デフォルト OFF）があり、設計判断を記録する ADR ファイルをレビュードキュメントの
隣に新規作成することを許可します（`{レビュードキュメント basename}-adr-{finding-id}.md`、
スケルトンは `rules/adr-format.md`）。見積時に、複数の実行可能なアプローチから
1 つを選んで修正方針を確定した指摘について見積サブエージェントが ADR を作成し、
ユーザーは `/creview:triage` と `/creview:respond` の間で ADR ファイルを編集
できます。レビュードキュメントの `Estimate:` メタデータから参照されている
ADR は、フラグに寄らず修正時に読み戻され（ユーザーが編集した Decision は
見積時のプランより優先）、Status / History が更新されます — `/creview:respond`
のフラグは、実装時に初めて生じた設計判断の ADR 新規作成のみを許可します。
後段のラウンドが同じ箇所を再修正した場合は、新規作成せず既存の ADR を更新または
Superseded にします。`/creview:rounds` も同じフラグを受け取り、両フェーズへ
そのまま渡します。

`/creview:rounds` には `--incremental` オプション（デフォルト OFF）があり、
2 ラウンド目以降は毎回ブランチ全体を再レビューするのではなく、前ラウンドの
開始時点以降に追加されたコミットのみをレビューします。Round 1 は常に
ブランチ全体の差分が対象です。有効にすると `--commit` も有効になります —
コミットされていない修正はどのラウンドのコミット範囲にも含まれないためです。
範囲の絞り込みは差分取得の時点で適用されます — `/creview:start` に、
指定したコミット範囲のみを取得しワーキングツリーのセクションを省く
`--range {from}..{to}` オプションが追加されています — そのため、
レビュアーが過去ラウンドでレビュー済みのコードを目にすることはありません。

`/creview:rounds` は最大 `--max-rounds` ラウンド（デフォルト 10、上限 20）まで
反復します。Round 2 以降はトリアージの後に発散パターン検出ゲートが入ります。
サブエージェントが過去ラウンドと今ラウンドのレビュードキュメントを読み、
指摘への修正が後のラウンドの指摘を生む連鎖を辿ります。3 ラウンド以上に
またがったまま縮小しない連鎖、または今ラウンドの指摘が過去の修正を元に戻すよう
求めている連鎖を発散とみなし、1 ラウンドで複数検出されることもあります。
1 件以上検出した場合は、調査サブエージェント（他の専門家と同様に移譲先
プロジェクトのエージェントから解決）が各発散の源泉を特定し、修正案を
レビュードキュメントの隣の `divergence-round{N}.md` に書き出します。その後
`--confirm` と同様にループを一時停止し、そのレポートを提示して続行の指示を
待ちます。続行の指示とともに修正方針が示された場合は、そのラウンドの対応
フェーズへ引き継ぎます。

`/creview:rounds` には `--worktree[=branch]` オプション（デフォルト OFF）があり、
全ラウンドを `.claude/worktrees/` 配下の別の git ワークツリーで実行します。
修正がメイン作業ツリーのソースに触れることはありません。ワークツリーは
`branch` をチェックアウトします — 既存のローカルブランチはそのまま、存在しない
場合は現在の HEAD から新規作成します。`=branch` を省略すると新しいブランチ
`creview-rounds-{timestamp}` を作成します。git は 1 つのブランチを 2 つの
ワークツリーでチェックアウトできないため、メイン作業ツリーでチェックアウト中の
ブランチは指定できません。有効にすると `--commit` も有効になります。
レビュードキュメント、最終レポート、各フェーズの作業用ディレクトリは
メイン作業ツリーの `.claude/tmp/` に置かれ、移譲先プロジェクトの
`.claude/agents/` と `.claude/rules/` もメイン作業ツリーのものを読みます。
各サブエージェントはワークツリーを作業対象（`target_dir`）として受け取り、
その配下・自身の作業用ディレクトリ・渡された出力先にだけ書き込み、
メイン作業ツリーを含むそれ以外のパスは参照のみとします。
ワークツリーはコミット済みの状態（新規ブランチなら現在の HEAD、既存の
ブランチならその先端）から始まるため、メイン作業ツリーの未コミットの変更は
実行に含まれません。gitignore 対象の依存物・仮想環境・ビルドディレクトリ・
`.env` や、`git worktree add` が初期化しないサブモジュールの中身もワークツリー
には存在しないため、ビルドとテストは新規チェックアウトで通る必要があります。
依存のインストール等は `build-format.md` の configure コマンドに含められますが、
configure はビルド段の冒頭でのみ実行されます（format コマンドより後で、ビルドが
スキップされた場合や宣言されていない場合は実行されません）。そのため、format
コマンドとビルドなしで走るテストは configure に依存できません。
そうした前提物の欠落によるビルド／テストの失敗はソースで修正せず、respond は
ビルド修正ループを打ち切って、その失敗をラウンドのワークフロー警告として記録し、
最終レポートに記載します。
各ラウンドのレビュードキュメントはワークツリーのブランチを記録するため、後から
それに対して実行した `/creview:triage`、`/creview:respond`、`/creview:resolve`
はそのブランチのワークツリーで作業します。
終了時にワークツリーは削除され、ブランチは残ります。
未コミットの変更が残ったワークツリーは削除せず、そのパスを報告します。
サブモジュールを初期化したワークツリー（configure で初期化した場合など）も git が
削除を拒否するため、同様に残してパスを報告します。内容を確認のうえ
`git worktree remove --force <パス>` で削除してください。残っている間は、同じ
ブランチを指定した `--worktree=branch` の再実行が失敗します。

ネスト起動（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`。デフォルトは 3）の
必要深度はエントリポイントごとに異なります。

- `/creview:rounds` — 3 以上。各フェーズをフェーズリーダーサブエージェントで
  実行し、そのサブエージェントが当該フェーズのサブエージェントを起動し、
  トリアージサブエージェントがさらに反証サブエージェントと裁定
  サブエージェントを起動します。
- `/creview:triage` 単体 — 2 以上。トリアージサブエージェントが反証
  サブエージェントと裁定サブエージェントを起動します。

長時間の実行はサブエージェントの枠を多く消費し、反証サブエージェントだけでも
指摘 8 件あたり 3 体、分割されたレビューは（スコープ, レビュアー）の組ごとに
1 体になるため、`--max-rounds` を大きくする場合は
`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`（デフォルト 200、セッション累積）の
引き上げを検討してください。並列に実行するサブエージェントは、
`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` のデフォルト値である 20 体ずつ起動し、
残りは後続のバッチで起動します。

## レビュアー / 修正担当エージェント

本節の末尾に挙げる同梱エージェントを除き、このプラグインは専門エージェントを
同梱しません。triage / scope-analysis /
analysis / format-build-verify / 発散パターン検出の各サブエージェントが**移植先プロジェクト**
（`.claude/agents/`）→**ユーザー**（`~/.claude/agents/`）→**プラグイン同梱**の順に、
サブディレクトリを含めて再帰的（`**/*.md`）にエージェントを列挙し、各エージェントの
frontmatter の `name` / `description` を読み、指摘ごとに最適なものを選定します
（scope-analysis はレビュースコープごとに、関連するエージェントをすべて選定
し、選んだエージェントがすべてコメントのみなどコードの振る舞いより狭い関心しか
扱わないスコープには `general-purpose` も加えます）。
一致が無い場合は `general-purpose` に
フォールバックします。同梱エージェントは `review-helper`（機械的な集約 / 検証）、
`comment-sensei`（コメント規律レビュー）、`review-leader`（`/creview:rounds` の
フェーズリーダー）、`pr-description-reviewer`（`/creview:start` の PR モードで
プルリクエスト本文と CI 結果をレビューする）、`pr-comment-compiler`
（`/creview:triage` と `/creview:resolve` の PR モードでプルリクエストのコメントから
指摘を抽出する）の 5 つで、最後の 2 つは使えるツールを制限したまま動かすために
同梱しています。このうち選定候補になるのは `comment-sensei` だけで、他の 4 つは
スキルが名前を指定して起動します。

## 日本語マスタ（リポジトリ直下 `src/creview/`）

日本語マスタはリポジトリ直下の `src/creview/` にあり、本プラグインのツリーを
1 対 1 でミラーします（`src/creview/skills/start/SKILL.md` ↔
`creview/skills/start/SKILL.md` など）。スキル名もプラグインと同一です。
ここにある実稼働の英語ファイルは、そのマスタを翻訳・変換して生成されます。
更新する際は `src/creview/` 配下の日本語マスタを編集し、その後実稼働ファイルへ
再翻訳・変換を再適用します（リネーム、パス書き換え、`review-respond` →
`triage` + `respond` の分割、エージェントディスパッチの一般化）。
