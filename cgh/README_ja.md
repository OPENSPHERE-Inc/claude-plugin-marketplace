# cgh

*[English README](README.md)*

[`creview`](../creview/README_ja.md) を土台にした GitHub プルリクエストのワークフローです。
すべてのスキルがプルリクエスト URL を受け取ります。内容を確認して投稿を指示するまで、GitHub には
何も送りません。このプラグインは承認、マージ、push、スレッドの解決を行いません。

## 必要なもの

- `creview` プラグイン 0.19.0 以降（Claude Code が依存関係として `cgh` と一緒にインストールします）
  と、そのプルリクエスト機能に必要なもの: 認証済みの GitHub CLI（`gh`）、Git 2.41 以降、
  `PATH` 上の `python3`（3.9 以降）、プルリクエストのリポジトリをリモートに持つクローン。それ以外の
  リポジトリのプルリクエストは、スキルが拒否します。
- スキルの開始時にオープン状態のプルリクエスト。push の後でマージされても、`/cgh:respond` は返信を
  投稿できます。
- リポジトリルートで開始したセッション。
- `.claude`、`.claude/tmp`、`.claude/worktrees` がシンボリックリンクではないプロジェクト。リンク先がプロジェクト内でも、
  同梱スクリプトがエラーで拒否します。作業ツリー間で設定を共有する場合は、`~/.claude/` に
  置いてください。

## スキル

| コマンド | 目的 | オプション |
|---------|---------|---------|
| `/cgh:review` | プルリクエストをレビューし、トリアージ済みの指摘を投稿する。 | `--adversarial`, `--trust`, `--adr`, `--force-comment` |
| `/cgh:gate` | セルフレビュー済みのプルリクエストがマージできるかを判定し、PASS / BLOCK を投稿する。 | `--adversarial`, `--trust`, `--adr`, `--force-comment`, `--incremental` |
| `/cgh:respond` | プルリクエストのレビューが求める修正を行い、返信する。 | `--no-confirm`, `--trust`, `--adr` |
| `/cgh:resolve` | 自分が挙げた指摘（`/cgh:review` の投稿または手書き）を検証し、結果を返信する。 | `--trust` |

### `/cgh:review`

`/creview:start` と `/creview:triage` を実行し、投稿内容を示して、指示を受けて投稿します。

レビューの前に、プルリクエストのコメントが既に指摘している問題を、自分と他の人、人間と AI を問わず集めます。
トリアージでは、挙げた人が解決まで確認することを期待できるので、それと同じ指摘を「既出（@name）」のような理由で
除外します。除外した指摘はプレビューの投稿しない指摘に表示され（Critical / Major は先頭に ⚠️ 付きで）、選択して
投稿することもできます。コメントが問題の原因、場所、影響を誤っていることをコードが示す
ときは、指摘を残します。

- **イベント**: 投稿する指摘に Critical または Major があれば Request Changes、なければ Comment。
  `--force-comment` を指定すると常に Comment。LGTM の判定は行いません。
- **内容**: 各コメントは深刻度と指摘 ID（`Critical C-1`、`Major M-1`、`Minor mi-1`）、
  レビュー文書のカテゴリタグ（`[バグ/セキュリティ]`）、指摘内容、人向けに要約した見積の推奨を
  含みます。コスト、シグナル、レビューエージェントは含みません。
- **デフォルトで投稿するもの**: Will Fix とトリアージされた指摘。見積が Downgrade とした Critical /
  Major も、問題がコードに残るので含みます。
  - Info、Won't Fix、Downgrade された Minor は、指示がない限り投稿しません。プレビューに理由とともに
    一覧されます。
- **投稿先**:

| 指摘の場所 | 投稿先 |
|------------------------|---------------|
| 差分内の行 | インラインコメント |
| 差分外の行で、ファイルは差分内 | ファイルレベルコメント |
| 差分外のファイル、またはファイルなし | レビュー本文 |

### `/cgh:gate`

すでにセルフレビューされたコード向けのマージゲートです。見るのは、壊れたコード、既存の挙動の
リグレッション、レビューが読めなかった変更、記録する issue のない残余（コードの `TODO`、PR 本文の
未完了項目、PR 本文やコードコメントが約束したフォローアップ）だけです。あった方がよい程度のテスト、
リファクタリング、スタイルは指摘しません。issue やプルリクエストを挙げている残余は記録済みとみなします。
会話コメントは残余を記録しません。観点は [rules/gate-focus.md](rules/gate-focus.md) にあります。

プルリクエストのコメントも、GitHub で resolved になったスレッドを含めてすべて読みます。議論の結論は、
コードか PR 本文に残っているか、PR 本文、コードコメント、または作者、アサイン先、自分のコメントが挙げる
issue やチケットで追跡されている必要があります。セキュリティ問題では、作者かアサイン先が挙げる追跡 issue
だけが記録になります。それ以外のコメントは記録になりません。

- こうして議論され記録された問題は、記録がコードと食い違っていない限り再度指摘しません。
  前提が誤っているとして却下された問題も、コードがそれを裏付けるなら指摘しません。
- そのどちらにも残っていない議論は、問題そのものの代わりに、完結していない議論として指摘し、ブロックします。
  PR 本文に 1 行書くか、追跡 issue をコメントで示せば解消できます。セキュリティ問題では、そのコメントは
  作者かアサイン先のものに限ります。
- 合意された変更や約束されたフォローアップは、話題によらず対象です。却下されたコメントは、問題がゲートの
  対象なら、コードが問題のないことを示さない限り対象です。未回答のコメントは、問題がゲートの対象で
  コードで成り立つときだけ対象です。

- **BLOCK**（Request Changes）: 投稿する指摘、または未検証の前回までのゲート指摘にブロッキングのものがあるか、
  プルリクエストにマージコンフリクトがある。
- **PASS**（Comment）: それ以外。PASS は承認ではありません。

`--force-comment` を指定すると、BLOCK も Request Changes ではなく Comment で送ります。

重大度とブロッキングは別のものです。Critical、Major、Minor は問題の影響の大きさだけを示します。各指摘は
トリアージの後に、ブロッキングか非ブロッキングかを個別に判定され、投稿するコメントの重大度の隣に示されます。

- 記録する issue のない残された作業、完結していない議論、レビューが読めなかった変更は、常にブロックします。
  PR 本文の未チェックの項目は、通常 Minor でブロッキングです。
- セキュリティ問題はブロックします。ただし、作者かアサイン先が、PR 本文、追跡 issue の提示、または決定者の却下で
  明示的に見送った場合を除きます。
- コメントでの却下だけなら通常は完結していない議論になり、PR 本文に記録するか追跡 issue を示すまでブロックします。
- その他の壊れたコードとリグレッションはブロックします。ただし、通常の使用では到達しない特殊な条件かごく短い窓でのみ
  発生し、見送りが PR 本文か決定者の却下から自明である場合の両方を満たすものを除きます。
- README など、人向けのドキュメントの問題は、セキュリティ問題でもブロックしません。AI 向けプロンプト、
  コード、PR 本文はここでのドキュメントに含みません。
- 判定のない指摘はブロックします。判定はプレビューで変更できます。

判定はレビュー本文に記載し、その後に短い総評を続けます。総評は、この回で何を確認し何が残るかを
述べ、作者が指摘を読む前にプルリクエストの状況をつかめるようにします。指摘は `/cgh:review` と同じ
ように配置し、カテゴリタグを付けて投稿します。

修正後、パスするまで繰り返し実行します。2 回目以降は、前回までのゲート指摘を現在のヘッドで
`/creview:resolve` により検証してレビュー本文で報告し、プルリクエスト全体を再度レビューします。修正
せずに受け入れる指摘は、スキルに取り下げを指示します: 以後の実行では再度報告しません。検証済みの前回までの
指摘も再度確認します: 解決が保たれていればレビュー本文に載せず、崩れていれば未検証に戻します。PR 本文の未完了項目は
PR 本文で検証し、項目が消えるか issue やプルリクエストを挙げていれば解決とします。タイトルや PR 本文の
主張はコードと PR 本文で検証し、コードが主張どおりに動くか、タイトルと PR 本文がもうその主張をして
いなければ解決とします。

`--incremental` を指定すると、プルリクエスト上のあなたの最新のゲートレビュー以降に追加された
コミットだけをレビューします。範囲は、GitHub がそのレビューについて記録しているコミットからヘッドまで
です。レビュー本文はそのコミットを示すため、PASS が差分全体を改めて確認したものではないことが読み手に
分かります。それ以外は指定がないときと同じです: 前回までのゲート指摘を現在のヘッドで検証し、議論の
ためにすべてのコメントを読み、PR 本文と CI 結果も改めて読みます。

- プルリクエスト上にあなたのゲートレビューがない場合、force push や rebase の後のようにヘッドが
  そのコミットをもう含まない場合、そのレビューの後にベースブランチが変更、force push、または削除
  された場合は、差分全体をレビューし、その理由を伝えます。
- dismiss したゲートレビューは数えません: 最新のものを dismiss すると、次の実行はその前のものから
  始まり、それもなければ差分全体をレビューします。
- その後にプルリクエストがベースブランチをマージしている場合、マージが持ち込んだものは除き、
  プルリクエストによるコンフリクトの解決と、マージが落としたベースの変更はレビューします。
  - バイナリファイルやベースが削除したファイルのように、マージがコンフリクトマーカーなしで
    コンフリクトのまま残したファイルは、ベースの版からレビューするため、そのファイルへの
    プルリクエストの以前の変更もレビューします。
- そのコミットより前のコードは再度レビューしません: 以前の実行が見逃した問題や、投稿しないと決めた
  指摘は、再度挙がりません。
  - 例外として、失敗したチェックと PR 本文の主張は、関わるコードがそのコミットより前にあってもヘッドの
    コードに照らして確認し、その行に報告します。
    - 行が見つからない主張は、プルリクエストに報告します。
    - 原因のコードが見つからない失敗したチェックは、報告しません。

### `/cgh:respond`

プルリクエストのコメントに `/creview:triage` を実行して結果を示し、確認を待ちます。その後
`/creview:respond --commit` を実行し、push を依頼します。push の後、コメントごとに 1 件、対応内容と
コミット、問題が既にコードにないこと、または変更しなかった理由を記した返信をドラフトします。内容を示し、指示を受けて投稿します。

- 確認の際に、指摘を修正の対象から外せます。その返信には、伝えた理由が記されます。
- トリアージの結果修正するものがなければ、確認を省いて返信のドラフトへ進みます。
- `--no-confirm` を指定すると、停止せずにトリアージから修正へ進みます。返信は指定の有無によらず
  指示を待ちます。
  - プルリクエストにコメントできる人は誰でも指摘に文面を入れられ、確認は修正前の最後のチェックなので、
    信頼できないプルリクエストには指定しないでください。
- レビュー本文や issue コメント由来の指摘への返信は、作者へのメンション付きの issue コメントになります。作者が bot ならメンションしません。
- スキルは、プルリクエストが修正コミットを含むまで返信を送りません。リベースするとハッシュが変わるので、
  そのまま push してください。リベースやスカッシュをしたらそう伝えると、スキルがコミットを集め直します。
- 対応されなかった指摘には返信しません。スキルがコメントを特定できなかった指摘にも返信せず、
  一覧で報告します。
- 指摘は CodeRabbit や Copilot など人間と AI を問わず誰のコメントからも取り上げ、対応済みかどうかは
  トリアージが会話とコードから判定します: コードに問題がもうない、そのレビューが dismiss された、
  プルリクエストの assignee（いなければ作者）が理由を述べて変更しないと決めた、または指摘したレビュアー
  本人が取り下げた場合です。
  - それ以外の人の発言は、これらの人が述べたと見なせるときだけ採用し、返信が述べる事実はコードで確認します。
  - 報告には Won't Fix とした指摘を場所、作者、理由とともに一覧します。
- 同じ趣旨の回答が誰かから既にあり、その後に蒸し返すものがないコメントには、変更しなかった旨の返信を
  繰り返しません。
- `/creview:respond` はプルリクエストのコードをビルドしテストします。信頼できないプルリクエストについては
  [creview README](../creview/README_ja.md) の警告を参照してください。

### `/cgh:resolve`

`/cgh:review` の投稿か手書きかを問わず、自分が挙げた指摘だけを `/creview:resolve` で検証し、返信を示して、
指示を受けて投稿します。各返信は確認したコミットを示します。コードが指摘の推奨どおりの修正なら、詳細は省きます。
Info の指摘は検証しません。

各指摘の状況（未対応、理由付きの見送り、検証済み、自分による取り下げ）は、サブエージェントが会話から判定します。
スレッドの返信を読み、レビュー本文や通常コメントの指摘についてはスレッド外の会話も読みます。

見送りはプルリクエストの assignee（いなければ作者）の回答に限り、それ以外の人の発言はこれらの人が述べたと
見なせるときだけ採用します。検証は見送りが述べる事実をコードで確認します。

後の変更で修正が崩れることがあるので、検証済みの指摘も毎回確認します。解決が保たれていれば返信せず、崩れていれば
その旨を返信します。見送りは修正か新しい見送りに置き換わるまで有効で、毎回その理由を検証します。理由に問題があると
判定されたら、`/cgh:respond` で修正または新しい理由を再度返信できます。

## 言語

コメントと返信は PR 本文の言語で投稿します。プレビューはあなたが使っている言語のままで、投稿する文面が
異なるときはそれも示します。すでに PR 本文の言語である指摘は翻訳しません。

## `--adversarial`

`/creview:start` に渡され、Critical / Major の指摘に具体的な失敗シナリオを求める敵対的モードで
レビュアーを実行します。[creview README](../creview/README_ja.md) を参照してください。

## `--trust`

HEAD がプルリクエストのヘッドにないとき、creview のスキルはプルリクエストの worktree で作業します。
この worktree はデフォルトでエージェントファイル（`CLAUDE.md`、`CLAUDE.local.md`、`AGENTS.md`、
`.mcp.json`、`.claude`）を含みません。そのためこれらのファイルの指摘は差分だけからレビューされ、
`/creview:respond` は修正しません。`--trust` はこれらを worktree に含めます。自分のチャットメッセージで
指定したときだけ有効です。

Claude Code はこれらのファイルを指示、スキル、設定として読み込むことがあるので、信頼できるプルリクエスト
に限るか、サンドボックス内で使ってください。[creview README](../creview/README_ja.md) を参照してください。

## `--adr`

`/creview:triage` に渡され、見積が設計判断を ADR ファイルとしてレビュードキュメントの隣に記録できるように
します。ADR はローカルに残り、投稿されません。`/cgh:respond` ではトリアージ後の確認でファイルを示すので、
修正の前に編集でき、`/creview:respond` がそれを読みます。`--no-confirm` を指定すると編集の機会はありません。
`/cgh:respond` は `/creview:respond` にも `--adr` を渡すので、修正中の設計判断も ADR ファイルに記録できます。

## 状態の保持

状態はプルリクエスト上にあるので、後の実行は前の実行のローカルファイルを必要としません。

- 人間と AI がこれらのスキルの有無によらず作業するので、指摘の状況は会話とコードから判定します。手書きの返信も
  スキルの返信と同じように扱います。
- コメントに隠しマーカーは入れません。人間と AI が混在するプルリクエストでは、マーカーが残ること、書き換え
  られないこと、偽造されないことを保証できないためです。サブエージェントは見えるテキストだけで判定し、誰の
  コメントでも読む前に HTML コメントを取り除きます。
- `/cgh:review` はすべてのコメントを見て、`/cgh:respond` は誰のコメントにも対応します。`/cgh:resolve` が確認するのは
  自分の指摘だけで、`/cgh:gate` はゲート自身の指摘だけです（議論としてはすべてのコメントを読みます）。
  レビューを dismiss すると、その指摘は確認と議論の対象外になります。
- GitHub でスレッドを解決済みにすると `/cgh:respond` では対応済みとして扱い、除外した数を報告します。
- 自分のコメントが使う指摘 ID は、サブエージェントが見えるテキストから文脈で読み取ります。新しい ID はその
  続きから採番するので、読み取りが正しい限り、プルリクエスト内の自分の指摘の中で一意です。
  `/cgh:review` のレビュードキュメントは独自に採番するので、投稿した ID がそのドキュメントの ID と
  異なることがあります。
- `/cgh:respond` はこの ID を保ちます。
  - 自分の指摘は、レビュードキュメント、プレビュー、報告で同じ ID になります。
  - 他の人の指摘には新しい ID を振ります。他の人が書いた ID は自分の ID と重複しうるためです。
    指摘に答える返信がその ID を示し、以後の実行で再利用します。それまでは実行ごとに ID が変わることが
    あります。
- `post` は送信した内容を読み直し、異なるものがあればその URL を報告します。

## 制限事項

- 投稿中に呼び出しが失敗したときは、GitHub 上のレビューの状態で判断します: それでも投稿されていれば投稿済み
  とし、保留中のままなら削除します。状態を読めないときはその旨を伝え、同じドラフトの再投稿を拒否します:
  再実行の前にプルリクエストを確認してください。
- レビューから投稿までの間にプルリクエストが進むと、スキルは投稿を拒否するので再実行します: 指摘の行番号は
  レビューしたヘッドのものです。
- `/cgh:gate` は、プルリクエストがマージできるかを GitHub が算出するのを待ち、算出が終わらないとき、
  プレビューの後に判定が変わったとき、レビューの後にプルリクエストのベースが変わったときは投稿を
  拒否します。
- `/cgh:gate`、`/cgh:resolve` は、確認する前回までの指摘があるときに、HEAD がプルリクエストに
  ないコミットを持つ、またはヘッド上に未コミットの変更があると停止します: 結果がプルリクエストにないコードの
  説明になるためです。
- GitHub は自分のプルリクエストへの Request Changes を拒否するので、その場合は Comment で送ります。
  `/cgh:gate` の判定はレビュー本文に残ります。
- PASS は Comment で送るので、以前に送った Request Changes を解除しません: dismiss されるまで GitHub に
  残り、dismiss するとそのレビューの指摘は以後の実行の対象外になります。
- GitHub ではプルリクエストごとに保留中のレビューは 1 ユーザー 1 件です。先に送信または破棄してください。
- 指摘 ID の読み取りと指摘の状況の判定は、実行のたびにサブエージェントが行うので、トークンを消費し、実行ごとに
  結果が変わることがあります。コメントのテキストから ID が消えたり読み違えたりすると、指摘に新しい ID が振られる
  ことがあります。
- コメントの文面はプルリクエストを読んだレビュアーに由来します。投稿前にスキルがコードの外の `@`
  メンションを除きますが、確実ではなく、それ以外は書かれたとおりに投稿されます。残った `@` メンションは相手に
  通知され、HTML コメントは GitHub 上で見えなくなるので、投稿前にプレビューを読んでください。
