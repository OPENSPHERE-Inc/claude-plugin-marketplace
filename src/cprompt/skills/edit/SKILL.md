# プロンプトエディタ

AI 向けプロンプト markdown を作成または編集する。完成したプロンプトは `${CLAUDE_PLUGIN_ROOT}/rules/prompt.md` を満たし、冗長さがなく、圧縮後も意図どおりに解釈される: 出力し、自己検査して修正し、圧縮し、テストで検証する。

人間向けドキュメント（README、API リファレンス、設計書等）は対象外。それらは `${CLAUDE_PLUGIN_ROOT}/rules/document.md` の管轄。

## 入力

ユーザーは以下のいずれかを指定する:

- 新規作成: 種別（agent / skill / rule / command / prompt）+ 対象パス + 要件
- 編集: 既存ファイルへのパス + 編集要件

引数 `$ARGUMENTS` は上記として解釈する。種別が明示されていない場合は対象パスから推測する:

- `.claude/agents/{name}.md` → agent
- `.claude/skills/{name}/SKILL.md` → skill
- `.claude/rules/{name}.md` → rule
- `.claude/commands/{name}.md` → command
- 上記以外（サブエージェント呼び出し本文の切り出し等） → prompt

## 出力規則

本スキルが作成・編集する対象に対して常に適用する。

### コードブロックに埋め込むサブエージェント向けプロンプト

スキル本文等で Agent ツールに渡すプロンプトを 3 連バッククォートのコードブロック内に埋め込む箇所は、原則プレーンテキストで書く:

- 見出し（`#` / `##` 等）、テーブル、強調装飾（`**` / `*` / `__`）は使わない。
- 列挙が必要な場合の箇条書き（`-` や `1.`）と、コード片や JSON 形式の例示は許容する。
- プレースホルダは `{...}` 形式に統一する（呼び出し側で埋める変数を示す）。

### markdown 出力テンプレートの外部化

編集対象のプロンプトが「生成する markdown の出力テンプレート（出力例の骨組み）」を含める場合、本文のコードブロックに埋め込まず、外部ファイルに切り出して参照する（markdown in markdown を避ける）:

- 配置先: 当該スキルの `templates/{name}.md`
- 本文には「テンプレート: `.claude/skills/{skill-name}/templates/{name}.md`（{利用主体}が Read して骨組みを把握する）」の形でパス参照のみ残す

例外（コードブロック埋め込みを許容）:

- 入力フォーマットの例示（編集対象のプロンプトが受け取るドキュメント / データ形式の説明）。
- JSONL / JSON / コマンドラインといった非 markdown フォーマットの例示。

## ステップ 1 — 出力作成

新規作成: 種別に応じたテンプレート `${CLAUDE_PLUGIN_ROOT}/skills/edit/templates/{種別}.md` を Read し、プレースホルダ（`{...}`）を要件に基づき具体化する（要件で言及されないセクションは削除してよく、要件が求める節は追加してよい）。Write で対象パスに出力し、対象パスのディレクトリが存在しない場合は `mkdir -p` で作成する。

編集: 対象パスを Read し、要件に基づき編集する。

## ステップ 2 — セルフチェックと修正

ゴール: 出力が `${CLAUDE_PLUGIN_ROOT}/rules/prompt.md` のどの項目にも違反しない状態。

1. 同ルールとステップ 1 で出力したファイルを Read し、違反箇所を `path:line` 形式ですべて列挙する。サブエージェント向けプロンプトのコードブロック内のプレーンテキスト原則違反と、3 連バッククォート（言語指定 `markdown`）で埋め込まれた出力テンプレート（入力フォーマット例示・非 markdown フォーマットは除外）も対象とし、後者は外部ファイルへ切り出してパス参照に置き換える。
2. 違反を Edit で修正し、修正により新たな違反が混入していないか再点検する。最大 2 回まで反復する。2 回目以降も残る場合はユーザーに残違反一覧を提示して判断を仰ぐ。

## ステップ 3 — 圧縮

ステップ 1 で出力したファイル（コードブロックに埋め込まれたサブエージェント向けプロンプト本文を含む）から冗長な記述を削減する。出力規則は圧縮中も引き続き適用する。以下の基準に該当する箇所を Edit で削減する:

- 「〜してください」等の丁寧表現は命令形に直す。
- 同じルールが複数箇所で繰り返されている場合は 1 箇所にまとめるか、参照に置き換える。
- AI が自然と判断できる規定は削除する（自明なエッジケースに対する逐一指示等）。
- 「A である。従ってこれは B ではない」のような `x == a && x != b` 形式の冗長な記述は前半のみに圧縮する。
- 不必要に冗長なコード例やテンプレートは最小骨組みに削る。

判定基準: 削減しても AI の取るべき行動が変わらないなら削減する。判断材料の WHY（制約・前提・誤解防止）は残す。

## ステップ 4 — テスト

サブエージェントにステップ 1 で出力したファイルを読ませ、過不足・誤解なく解釈されるかを確認する（特にステップ 3 の圧縮で意味が損なわれていないかを検出する）。

1. チェック項目を作成する。チェック項目は「このプロンプトを読んだエージェントが特定の状況でどう振る舞うべきか」を質問形式で列挙する（例: 入力に種別が含まれない場合の判定方法、ステップ X が失敗した時のフォールバック、ステップ間の入出力の流れ、各分岐条件の閾値など）。対象プロンプトの入力仕様・各ステップ・分岐条件・出力仕様をカバーするように選ぶ。
2. Agent ツールでテストサブエージェントを起動する。プロンプト:

```
プロンプト解釈テスト担当。{prompt_path} を Read し、以下の各チェック項目に、そのプロンプトから読み取れる情報のみで 1〜2 文で回答する。外部知識や推測は使わない。プロンプトから読み取れない / 曖昧 / 矛盾する項目は unclear として理由を 1 文添えて報告する。修正提案や編集はしない。

チェック項目:
1. {項目 1}
2. {項目 2}
...

戻り値: {pass, unclear_items: [{item, reason}]}（unclear_items が空配列なら pass: true）
```

3. 戻り値が `pass: true` なら終了。
4. `unclear_items` があれば該当箇所を Edit で明確化し、本ステップを再実行する。最大 3 回まで反復する。3 回目以降も残る場合はユーザーに残 unclear 一覧を提示して判断を仰ぐ。

## ステップ 5 — 完了報告

対象パス、検出/修正された違反件数、圧縮の有無、テスト結果（pass / 残 unclear 一覧）を報告する。
