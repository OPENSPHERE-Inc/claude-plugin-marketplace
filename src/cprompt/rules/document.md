# ドキュメンテーション規律

ドキュメントを書いたり修正したりする際は、以下のルールに従うこと。

本ルールは AI 向けプロンプト（`.claude/` 配下のエージェント定義、スキル、コマンド、ルール等のプロンプト類）には適用しない。

## 読者を意識する

- **ドキュメントは対話中のユーザーではなく、後で参照する第三者に向けて書く。** チャット文脈に依存した主観的な書き方は避けること。第三者は「ユーザーがどう依頼したか」「以前のドキュメントがどうだったか」「どのファイルから移植したか」を知らない。
  - NG 例: 「ユーザーの要望により〜を追加」「以前は〜だったが今回〜に変更」のように対話コンテキストを前提とした記述。
  - 代わりに: ドキュメント自体から読み取れる事実・仕様・前提のみを、対話の経緯に依存しない形で記す。変更経緯は git log / PR 説明に残し、ドキュメント本文には残さない。
- **例外**: ユーザーが明示的にそうした記述を求めた場合や、対話コンテキストの延長として生成するドキュメント（プラン、レポート、議事録等）はこの限りではない。

## 参照の独立性

- **第三者が参照できる形でドキュメント化されていない事柄を参照しない。** 口頭の決定、Slack の発言、対話履歴、未公開資料等を根拠として記述しない。
  - 参照するなら、第三者がたどれる場所（リポジトリ内のファイル、公開 URL、発行済み仕様書等）を明示すること。
  - 該当する公的な参照先がない場合は、参照そのものを書かず、ドキュメント内で完結する記述に書き換えること。

## Markdown の記法

- **テーブル内のインラインコードに `|` を含める場合はエスケープする。** インラインコード内であっても、Markdown のテーブルセル区切りは `|` で行われるためパースが破綻する。`\|` でエスケープすること。
  - NG 例: `| 演算子 | `a | b` で OR を表す |`
  - OK 例: `| 演算子 | `a \| b` で OR を表す |`
- **Markdown ソースは適切に改行する（目安: 最大 100 文字）。** 長い段落を 1 行に詰め込まず、文や節の区切りで改行して可読性と差分の見やすさを確保すること。
  - 例外: Markdown のフォーマット上、改行が許されない箇所（テーブル行、見出し行等）はこの限りではない。
- **Markdown の単一改行はレンダリング結果に反映されない。** ソース上の改行はビューワーで空白として扱われ、同一段落として表示される。表示上で行を分けたい場合は、以下のいずれかを使うこと。
  - 段落として分ける場合: 空行を挟む。
  - 列挙として分ける場合: リスト（`-` や `1.`）にする。
  - どうしても段落内で改行したい場合: 行末に半角スペース 2 つ、もしくは `<br>` タグを使う（多用しない）。
