# プロンプト規律

エージェント定義、スキル、コマンド、ルール等の AI 向けプロンプトを書いたり修正したりする際は、以下のルールに従うこと。

本ルールは人間向けドキュメント（README、API リファレンス、設計書等）には適用しない。人間向けドキュメントは [document.md](document.md) の対象。

## 契約型プロンプト

AI 向けプロンプトはプログラムコードではない。曖昧な指示でも AI は文脈から要件をある程度推論するため、一貫性・再現性が要求されない箇所に厳格な手続き指示は書かない。

- ゴールは具体的に明示し、そこへ至る手法は実行する AI に委ねる。手続きを詳細化しすぎない。
- チェックポイントで守るべき契約は明記する。指定の形で実行させたいコマンド、返り値のフォーマット等が該当する。
- 厳密なコマンドライン・実行フローが必要な場合は外部スクリプト化を検討し、プロンプトにはその呼び出しと期待する結果を書く。
- 推奨パターン: 得るべき結果（ゴール）を明示し、使用すべき道具（ツール）を配備する。
- アンチパターン: 実行コマンドラインをプロンプトに手続き的に列挙して従わせる。

## 読者は AI

- プロンプトの読者は AI エージェントである。ユーザーや第三者の人間に向けた解説的記述は不要。
- 「このプロンプトは〜のために作られた」「以下では〜について説明する」のようなメタ説明は書かない。指示そのものを書く。
- 経緯・背景・動機の説明は、AI の判断に必要な範囲に限る。AI の作業に影響しない経緯は書かない。

### 避けるべきメタ説明パターン

以下のパターンは AI runtime 行動に影響しないので削除する。リスト各項目は具体例の集合であり、最終判定は本セクション末尾の判定基準に従う。1 文中に複数パターンが混在する場合は、該当部分のみを削除し、現ステップの作業指示部分は保持する。

- 動作の効果を再記述する: 「X する。これにより Y される」「X することで Y を達成する」「X して Z に伝達する」（直前の動作の効果は動作自体に内包される）
- 動作の意図を強調する: 「確実に Y する」「漏れなく X する」「必ず Z する」（指示動詞自体に意図は含まれる）
- 説明的前置き: 「以下では...」「このセクションは...」「次に〜について述べる」「〜を行うには」（同一プロンプト/セクション内の構造案内であり、本文を読めば自明）
- 編集者向けの保守ガイドライン: 「重複記載は避ける」「将来の保守者は X せよ」「コードを編集する際は...」（AI runtime 作業ではなく、SKILL や Rule 自体の編集方針）
- 他ステップへの先読み: 「これはこのステップでは行わない。ステップ N で行う」「集約は次ステップで実施する」（現ステップの作業実行に不要な、別ステップの作業に関する情報。説明的前置きが同一プロンプト内構造の案内なのに対し、本項は別ステップ作業への言及）

判定基準: 各文を削除した時に AI の取るべき行動が変わるか? 変わらなければ削除する。本判定基準は上記リスト全項目に適用する。

### 判断材料の WHY と効果説明の WHY

WHY 説明は二種類ある。前者は残し、後者は削除する。

- **判断材料の WHY** (残す): AI がエッジケースで判断する際の制約・不可視の前提・誤解防止のための補足。
  - 例: 「cat heredoc は値内のアポストロフィでクォーティング破綻するため不可」（「アポストロフィが無ければ OK?」という誤解防止）
  - 例: 「C API 境界を越えて C++ 例外を投げない（ABI 不一致防止）」（制約の根拠提示）
- **効果説明の WHY** (削除): 直前の動作の effect を再記述するもの。
  - NG: 「Append する。これにより Sub に伝達される。」← append 自体が伝達。
  - NG: 「Read する。これによりデータを取得する。」← Read 自体が取得。
  - 判定: 動作それ自体に効果が内包されているか。Yes なら削除。

### 保守ガイドラインと runtime 指示の分離

- AI runtime 指示: AI が読んで実行する具体的アクション。プロンプトに記載する。
- 保守ガイドライン: プロンプト・スキル・ルール自体の編集方針。AI runtime には影響しない。
  - NG: 「共通ルールは重複記載しない」「Sub プロンプトに meta 説明を含めない」（プロンプト編集時の方針）
  - 対処: 本ファイル（prompt.md）等のメタルールに集約するか、削除する。個別プロンプト本文には書かない。

## 構造と装飾

- 過度な装飾は不要。見出し階層は最小限に保つ。
- 改行は必要最低限。段落を空行で区切る程度で十分。
- テーブルは原則使わない。箇条書きに置き換える。
  - 例外: AI に出力フォーマットを指定する場合、出力例としてテーブルを示すのは可。
- 強調（`**` や `*`）は本当に重要な箇所のみ。多用すると意味が薄れる。

## コンテキスト依存の排除

- チャット文脈に依存した記述は書かない（[document.md](document.md) と同方針）。
- 「ユーザーがこう言ったので」「以前のプロンプトでは」のような対話履歴前提の記述は避ける。プロンプトはそれ単体で完結させる。

## 含める内容

- エージェントが作業に必要な指示とコンテキストのみ含める。
- 余談・補足・「念のため」の情報は省く。AI は冗長な指示で精度が下がる。
- 指示は具体的に書く。曖昧な指示（「適切に」「いい感じに」等）は避け、判断基準を明示する。

## 出力フォーマットの指示

- AI が Markdown を出力する場合、Markdown ビューワーは単一改行を改行としてレンダリングしないことに注意する。
  - 行を分けて表示させたい場合は、リスト（`-` や `1.`）にするか、空行で段落を区切る。
  - 単純に `\n` を入れただけでは、レンダリング後に空白区切りの 1 段落として表示されてしまう。
- AI に Markdown 出力を指示するときは、この点を踏まえてフォーマット指定を書くこと。
