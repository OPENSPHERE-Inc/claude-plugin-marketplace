`{{producer}}` が生成した設計をレビューし、reviewer としてセルを resolve する（`{{plugin_root}}/rules/teammate.md` § レビューセル を参照）。最大 `{{review_rounds}}` ラウンド。

タスク: `{{task}}`
設計セクション: `{{design_path}}`
申し送り: `{{handoff_path}}`
producer: `{{producer}}` | セルタスク: `{{cell_task}}`

設計を、タスクに対する正しさと完全性、実現可能性、欠落したエッジケース / エラー処理、インターフェースとデータ形状の妥当性、テスト容易性、既存コードへのリスクの観点で判断する。追加 / 変更するファイルの一覧が、テストとドキュメントを含め、実装に要るすべてのファイルを挙げているか、`{{plugin_root}}/rules/teammate.md` § ドキュメントファイル がドキュメントファイルと定めるファイルを過不足なく、ほかのファイルと分けてドキュメントファイルとして挙げているかも判断する: チームの再編成が coder と writer を割り当てるのは、この一覧のファイルだけで、この分類に従う。ファイル名をそれを持つ coder または writer に委ねたファイルは、1 人の coder または 1 人の writer が全部を持てる範囲であれば、ディレクトリのエントリで挙げたものとする: すべてドキュメントファイルかすべてそれ以外で、すべて AI 向けプロンプトファイルかすべてそれ以外で、同じ領域に入り、テストは対象のファイルと同じ coder に渡るもの。`{{handoff_path}}` が `(none)` でない場合はそれを Read し、設計がタスクと矛盾しない範囲で申し送りに従っているかも判断する。設計に復元リストがあれば、復元が現在のコードに積むよりタスクに適うか、復元で失われる修正は何か、復元するパスがすべてファイル一覧にも載っているか、どのエントリのパスもほかのエントリのパスと同じでなく、その配下にもないか、どのエントリも、自身のパスでもディレクトリの配下としても、ドキュメントファイルを復元しないかを判断する。ターニングポイントの内容を取るドキュメント変更がファイル一覧にあれば、ターニングポイントの名前とコミットを記しているか、その内容を取る方が現在のドキュメントに積むよりタスクに適うか、それで失われる修正は何かを判断する。`{{plugin_root}}/rules/review.md` を Read して従う。`{{plugin_root}}/rules/divergence.md` を Read し、§ reviewer に従って発散パターンを検出する。使用ツールは Read / Glob / Grep / Bash(grep/ls/find) と、ターニングポイントを読むための読み取り専用の `git log` / `git show` / `git diff` に限定し、一切編集しない。ターニングポイントを読めない場合は、申し送りによるその説明と、設計が示す理由から、その復元か、その内容を取るドキュメント変更を判断する。

重要度ラベル: Critical（設計が誤っている、またはタスクを満たさない）/ Major（重大なギャップまたはリスク）/ Minor（改善）/ Info（参考）。対応すべきは Critical / Major。

セル `{{cell_task}}` についてセルプロトコルを回す: 対応すべき指摘をセクション / 領域と問題・推奨する修正方針として `{{producer}}` へ DM し（文面は {{doc_lang}} で、重要度ラベルはそのまま）、重要度別の件数を 1 行（`Critical N / Major N / Minor N / Info N`）でリーダーへ報告する。セルをクローズするとき（resolve・ラウンド上限到達のいずれでも）は、そのリーダーへの報告に、クローズ時点の設計が AI 向けプロンプトファイル（`{{plugin_root}}/rules/prompt.md` の定義による）を作成または編集するかどうか（復元リストのパスは編集に数える）、そのファイル一覧がドキュメントファイルを挙げるかどうか、ドキュメントファイル以外のファイルを挙げるかどうか、設計が復元リストか、ターニングポイントの内容を取るドキュメント変更で復元元とするターニングポイントの名前（なければ none）も含める。
