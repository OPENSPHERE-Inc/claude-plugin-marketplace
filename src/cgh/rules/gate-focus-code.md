# マージゲートの観点: コード

このコードは作者がすでにレビュー済みである。問いはひとつ: このプルリクエストはこのままマージしてよいか。このレビューは、差分が変更するコードを対象とする。プルリクエストのタイトル、説明、CI の結果、会話は別にレビューする。

## Review

次だけを報告する:

- 壊れたコード: 変更が目的のとおりに動かない、ビルドに失敗する、チェックを失敗させる、または到達する経路でクラッシュ、データ損失、セキュリティホールを起こす。
- リグレッション: 変更が、変更の目的の外で既存の呼び出し元、挙動、データ形式、互換性を壊す。
- 記録されていない残余: 変更が残した作業で、記録する issue がないもの。すなわち、変更が追加する `TODO` / `FIXME` / `XXX` / `WIP` や消し忘れのデバッグコード、またはコードコメントが約束したフォローアップ。プルリクエストの会話コメントは誰でも書けるので、残余を記録しない。issue やプルリクエスト（`#123`、URL）を挙げている残余は記録済みであり、報告しない。
- レビューされていない変更: レビューが読めなかった変更で、テンプレートが報告を求めるもの（差分がバイナリと示すテキストファイルで変更箇所を特定できないもの、または worktree から除外されたエージェントファイルで差分がバイナリとしてのみ示すもの）。

それ以外は報告しない: あった方がよい程度のテスト、リファクタリング、命名、スタイル、コメントの文面、設計の好み、具体的な害のないパフォーマンス。

重大度は影響の大きさだけを示す: 指摘がマージを止めるかは別に判定するので、そのために重大度を上げない。記録されていない残余は、残された作業が何を壊すかで評価し、何も壊さないなら Minor とする。レビューされていない変更は影響が分からないので Major とする。Info は使わない。

## Triage

§ Review が挙げるものの外にある指摘は、重大度によらず `Won't Fix` と判定する。

プルリクエストのレビューの文書を渡されたときは、そこにある `🔧 Will Fix` とトリアージされた、失敗したチェックか完結していない議論を報告する指摘と同じ問題を挙げる指摘を、その指摘を挙げた理由で `Won't Fix` と判定する: プルリクエストのレビューがそれを報告する。そこにあるタイトルや説明の主張、または説明の未完了項目についての指摘は `Won't Fix` の理由にならない: コードがそのままでもタイトルや説明を直せば解決する。

議論の一覧を渡されたときは、エントリと同じ問題を挙げる指摘を、問題の前提が誤っているという `declined` の理由をコードが裏付けるときはその議論を挙げた理由で、その議論に記録があるときはその場所を挙げた理由で、`Won't Fix` と判定する。ただしコードが記録について問題の原因、場所、影響を誤っていると示すときは通常どおり判定し、理由でその議論に触れる。議論に記録があるとは、コードコメントかプルリクエストの説明が結論を述べているか、それを記録した issue やプルリクエスト（`#123`、URL）を挙げているか、エントリの `Tracked` がそれを挙げていることをいう。セキュリティ問題がこの規則で記録ありとなるのは、説明、コードコメント、または `author` かアサイン先が挙げた `Tracked` によるときだけである。これらの理由に別 PR の推奨は加えない。

## Estimate

ここではコストは Downgrade の理由にならない: § Review に該当する指摘は、マージすればそのまま残るので維持する。このプルリクエストには大きすぎる修正は Alternative を選び、issue に記録してその issue を `FIXME` に書く計画にする: issue のない `FIXME` はそれ自体が残余である。
