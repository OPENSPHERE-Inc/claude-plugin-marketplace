# マージゲートの観点: プルリクエスト

このプルリクエストは作者がすでにレビュー済みである。問いはひとつ: このままマージしてよいか。このレビューは、プルリクエストのタイトル、説明、CI の結果、会話を、その差分全体に照らして対象とする。コードそのものは別にレビューする。

## Review

次だけを報告する:

- 失敗したチェック: 完了したチェックを失敗、タイムアウト、キャンセルさせる変更行で、テンプレートが述べるもの。
- コードが反する主張: タイトルや説明が述べる変更（変更が何をするか、修正する issue、存在する・通るとされるテスト）のとおりに動かない変更行、またはタイトルや説明が主張する変更で差分がしていないもの。
- PR 本文の記録されていない残余: PR 本文の未チェックのタスクや TODO / WIP の記述、または PR 本文が約束したフォローアップで、記録する issue がないもの。プルリクエストの会話コメントは誰でも書けるので、残余を記録しない。issue やプルリクエスト（`#123`、URL）を挙げている残余は記録済みであり、報告しない。
- 完結していない議論: 議論の一覧を渡されたとき、§ Discussions に従う。

PR 本文の残余と、タイトルや説明が主張する変更で差分がしていないものは、指摘を変更行と `file_path:line` に結び付け、差分のどこにも関わらない主張を指摘としないテンプレートの規則に代えて、場所を `PR` とし、項目または主張を引用して報告する。

それ以外は報告しない: 別にレビューするコードそのものの問題、説明が書いていない変更、タイトルや説明の文面。

重大度は影響の大きさだけを示す: 指摘がマージを止めるかは別に判定するので、そのために重大度を上げない。失敗したチェックは何が失敗するかで、コードが反する主張はそれを信じると何を誤るかで評価し、タイトルや説明が古いだけなら Minor とする。記録されていない残余は、残された作業が何を壊すかで評価し、PR 本文の未チェックの項目のように何も壊さないなら Minor とする。Info は使わない。

## Discussions

プルリクエストのコメントでの議論の結論は、コードか記録に残らなければならない: コメントだけでは完結しない。渡された一覧の各エントリは、コメントで挙げられた問題とその回答、結論である。誰でもコメントできるので、未確認の主張である。

議論は、次のいずれかを満たすとき完結している:

- HEAD のコードが結論のとおりになっているか、問題の前提が誤っているという `declined` の理由を裏付けるときのように、問題がないことを示している。コードが変わっていないことは、維持の決定を示さない。`declined` の理由がコードでは示せない事実に基づくときは、この条件を満たさず、その議論を完結させられるのは記録だけである。
- 記録がある: コードコメントかプルリクエストの説明が結論を述べているか、それを記録した issue やプルリクエスト（`#123`、URL）を挙げている。またはエントリの `Tracked` がそれを挙げている。セキュリティ問題では、その `Tracked` は `author` か `assignee` が挙げたものに限る。それ以外の会話のコメントやスレッドの resolved 表示は記録に当たらない。

ゲートが探す問題とは、壊れたコード、既存の挙動のリグレッション、記録する issue のない残された作業、レビューが読めなかった変更、失敗したチェック、コードが反する主張である。完結していない議論は、結論が `agreed` か `promised` なら話題によらず報告し、`declined` なら問題がゲートの探すものであるときに報告し、`none` なら問題がゲートの探すもので、かつコードで成り立つときに報告する。それ以外のエントリは報告しない。

挙げられた問題の影響で重大度を評価し、コメントの `path:line` が変更行ならそこで、そうでなければ、指摘を変更行と `file_path:line` に結び付けるテンプレートの規則に代えて、場所を `PR` として報告する。完結していない議論であることを述べ、問題、挙げた人と場所、回答、そしてコードへの反映、説明への記録、issue での追跡のいずれかが必要であることを書く。

## Triage

§ Review が挙げるものの外にある指摘は、重大度によらず `Won't Fix` と判定する。場所が `PR` の残余には判断の材料となるコードがない: 引用された文面で判断する。場所が `PR` の主張された変更は、引用された主張を HEAD のコードに照らして判断する。

議論の一覧を渡されたとき:

- 完結していない議論を報告する指摘: § Discussions でその議論が完結していると判断できるとき、またはその規則でエントリを報告すべきでないときは `Won't Fix` と判定する。
- エントリと同じ問題を挙げるその他の指摘: 文書にその議論を完結していないと報告する指摘があり、その指摘を前項で `Won't Fix` と判定しないときは、その旨の理由で `Won't Fix` と判定する。問題の前提が誤っているという `declined` の理由をコードが裏付けるときは、その議論を挙げた理由で `Won't Fix` と判定する。その議論に記録があるときは、その場所を挙げた理由で `Won't Fix` と判定する。ただしコードが記録について問題の原因、場所、影響を誤っていると示すときは通常どおり判定し、理由でその議論に触れる。セキュリティ問題がこの規則で記録ありとなるのは、説明、コードコメント、または `author` かアサイン先が挙げた `Tracked` によるときだけである。これらの理由に別 PR の推奨は加えない。

## Estimate

ここではコストは Downgrade の理由にならない: § Review に該当する指摘は、マージすればそのまま残るので維持する。失敗したチェックは、その原因を直す計画にする。コードが反する主張は、コードを主張どおりにするか、タイトルや説明を直す計画にする。場所が `PR` の残余は、項目を PR 本文から除くか、issue に記録してその issue を PR 本文に書く計画にする。完結していない議論は、結論のとおりに対応するか、結論を説明または issue に記録する計画にする。このプルリクエストには大きすぎる修正は Alternative を選び、issue に記録してその issue を説明に書く計画にする。
