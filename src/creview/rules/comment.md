# コメント規律

コードを書いたり修正したりする際は、以下のコメントルールに従うこと。

- **コードを直し、長文で弁明しない。** 「なぜ現状で安全か」を段落コメントで説明すると可読性を下げ、次のレビューで再び文言が争点になる。
- **先送りは FIXME で、根拠説明はしない。** 根本修正がスコープ外の場合（別 PR 対応、設計判断保留、意図的な先送り）は、短い `FIXME:` / `TODO:` を残す（1〜2 行で問題と推奨修正方針を記す）。網羅的な根拠説明は書かないこと。
- **長めのコメントは、本当に非自明な不変条件がある場合のみ。** コードから推測できない不変条件に限る。その場合も 1 段落にとどめる。
- **コメントは対話中のユーザーではなく、後でコードを読む第三者に向けて書く。** チャット文脈に依存した主観的な書き方は避けること。第三者は「ユーザーがどう依頼したか」「以前のコードがどうだったか」「どのファイルから移植したか」を知らない。
  - NG 例: リファクタリングで `a` から `b` にロジックを移した際に、`// オリジナル a のロジックを b では ... のように修正` と書く。第三者にとっては `a` の存在も移植の経緯も不明であり、対話コンテキスト前提の記述は通用しない。
  - 代わりに: コメントが必要なら、コードそのものから読み取れない不変条件・制約・前提のみを、コードベース内で完結する形で記す。変更経緯は git log / PR 説明に残し、コメントには残さない。

本ルールはコードコメントに適用される。ユーザー向けドキュメント（API リファレンス、README 等）は対象や制約が異なるため、本ルールの対象外。
